Tool use and function calling

Tool use and function calling extend Large Language Models beyond closed-world text generation by connecting them to external APIs, calculators, databases, and code execution environments. Rather than relying on memorised weights for complex arithmetic, real-time data, or system actions, tool-augmented models emit structured function call invocations (typically adhering to strict JSON Schema specifications). The host runtime executes the tool and injects the output back into the message history, enabling reliable agentic workflows.

01 The idea

Ask a pure Large Language Model to calculate 347,291 multiplied by 984,123, and it will confidently guess a plausible-looking but completely incorrect number. Ask it what the weather is in Tokyo right now, and it will hallucinate a forecast based on training data from two years ago. Pure language models are closed worlds. Function calling gives models hands and eyes: when arithmetic is needed, the model calls a calculator; when live data is needed, it calls a weather API; when action is required, it calls a database mutation.

The limits of closed-world parametric memory: Neural network weights represent static parametric memory frozen at training time. They suffer from three fundamental limitations: 1. Knowledge Cutoff: Inability to access live or real-time information (e.g. stock prices, news, flight status). 2. Calculation Inaccuracy: Large numbers and multi-digit arithmetic fail because tokenisers fragment numbers unpredictably. 3. Inability to Act: Pure text generation cannot execute database writes, book appointments, or send emails. Tools decouple reasoning from execution: the model serves as the cognitive orchestrator, delegating specialised operations to external software tools.

The Function Calling Protocol: How does an LLM invoke an external tool? 1. Tool Definition: Developers register tool definitions in the system prompt using JSON Schema, specifying the tool name, description, parameters, and required fields. 2. Model Decision & Tool Call Emission: When a user query requires a tool, the model pauses natural prose generation and outputs a structured tool invocation object: { "name": "get_weather", "arguments": { "city": "Tokyo" } }. 3. Client Runtime Execution: The host client receives the tool call, executes the actual Python function or REST API, and captures the result. 4. Continuation: The client appends the tool output to the message transcript with role: "tool". The model ingests the real-world result and continues generating its response.

Multi-step tool chaining and error handling: Sophisticated agentic workflows require chaining multiple tools sequentially. For example, to answer "How much did our top customer spend last month?", the model first calls a SQL tool to look up the top customer's ID, inspects the returned ID, calls a second tool to fetch their transaction records, and finally computes the summary. If a tool call fails (e.g. invalid arguments or API timeout), the error message is fed back into the context, allowing the model to self-correct its arguments.

In everyday terms

Think of a brilliant business executive who does not know how to fly a Boeing 777 or write raw SQL database queries. When the executive needs to travel to a conference in Geneva, they do not attempt to construct an aeroplane out of sheet metal. They summon their administrative travel assistant (a specialized tool), state their objective, and let the booking system execute the flight reservation. The executive remains the high-level decision-maker, delegating technical mechanics to specialised tools.

03 The maths

  1. Tool Augmented Language Model objective

    P(y \mid x, \mathcal{T}) = \sum_{a \in \mathcal{A}_{\mathcal{T}}} P(\text{Call}(a) \mid x) \cdot P(y \mid x, a, \operatorname{Exec}(a))

    Here $\mathcal{T}$ is the set of available tools, $\text{Call}(a)$ represents generating a structured tool invocation with arguments $a$, $\operatorname{Exec}(a)$ is the external runtime execution result, and $y$ is the final synthesized natural language response.

  2. Structured JSON Schema validation predicate

    \operatorname{Valid}(\mathbf{a}, \mathcal{S}) = \begin{cases} 1 & \text{if } \forall k \in \mathcal{S}_{\text{req}}: k \in \mathbf{a} \land \operatorname{type}(\mathbf{a}[k]) = \mathcal{S}_{\text{type}}[k] \\ 0 & \text{otherwise} \end{cases}

    A tool argument payload $\mathbf{a}$ emitted by the model is valid if and only if all mandatory schema fields $\mathcal{S}_{\text{req}}$ are present and their types match declared specifications $\mathcal{S}_{\text{type}}$.

  3. Tool invocation decision threshold

    \text{Decision} = \begin{cases} \text{Invoke Tool } t^* & \text{if } \max_{t \in \mathcal{T}} P(t \mid x) > \gamma_{\text{threshold}} \\ \text{Generate Direct Response} & \text{otherwise} \end{cases}

    Function-calling models learn a calibrated binary decision boundary to determine whether a user query requires external tool assistance or can be answered directly from parametric memory.

04 Key takeaways

  • Tool use connects Large Language Models to external APIs, databases, code interpreters, and real-time data sources.
  • Function calling protocols use JSON Schema to specify tool names, descriptions, and strongly typed parameter definitions.
  • The model acts as a reasoning orchestrator: it outputs structured JSON function calls, pausing generation until the host runtime returns execution results.
  • Tool execution occurs client-side in the host runtime, maintaining security and sandboxing boundaries outside the neural model.
  • Multi-turn tool chaining enables complex agentic workflows: models inspect intermediate outputs and iteratively invoke subsequent tools.

05 In code

python
import json

class ToolCallingEngine:
    """
    Simulation of an LLM tool calling dispatch engine with schema validation,
    execution dispatch, and response formatting.
    """
    def __init__(self):
        self.tools = {}
        self.schemas = {}

    def register_tool(self, name, description, schema, func):
        self.tools[name] = func
        self.schemas[name] = {
            "name": name,
            "description": description,
            "parameters": schema
        }

    def validate_and_execute(self, tool_call_json):
        """Validate JSON tool call against schema and execute."""
        try:
            call = json.loads(tool_call_json)
            tool_name = call.get("name")
            args = call.get("arguments", {})
            
            if tool_name not in self.tools:
                return {"status": "error", "message": f"Unknown tool '{tool_name}'"}
                
            schema = self.schemas[tool_name]["parameters"]
            # Validate required fields
            for req in schema.get("required", []):
                if req not in args:
                    return {"status": "error", "message": f"Missing required parameter: '{req}'"}
                    
            # Execute function
            result = self.tools[tool_name](**args)
            return {"status": "success", "result": result}
        except Exception as e:
            return {"status": "error", "message": str(e)}

# Define tool implementations
def calculate_mortgage(principal, rate, years):
    """Compute monthly mortgage payment: P * (r(1+r)^n) / ((1+r)^n - 1)"""
    r = rate / 100.0 / 12.0
    n = years * 12
    monthly = principal * (r * (1 + r)**n) / ((1 + r)**n - 1)
    return round(monthly, 2)

def get_exchange_rate(source_curr, target_curr):
    """Mock currency exchange rate API."""
    rates = {("GBP", "USD"): 1.30, ("EUR", "USD"): 1.08, ("USD", "JPY"): 152.0}
    return rates.get((source_curr.upper(), target_curr.upper()), 1.0)

# Initialize Engine and register tools
engine = ToolCallingEngine()

engine.register_tool(
    name="calculate_mortgage",
    description="Calculate monthly mortgage repayment amount for a property loan.",
    schema={
        "type": "object",
        "properties": {
            "principal": {"type": "number", "description": "Loan amount"},
            "rate": {"type": "number", "description": "Annual interest rate percentage (e.g. 4.5)"},
            "years": {"type": "integer", "description": "Loan term duration in years"}
        },
        "required": ["principal", "rate", "years"]
    },
    func=calculate_mortgage
)

engine.register_tool(
    name="get_exchange_rate",
    description="Get live currency exchange rate between source and target currency codes.",
    schema={
        "type": "object",
        "properties": {
            "source_curr": {"type": "string", "description": "3-letter source currency (e.g. GBP)"},
            "target_curr": {"type": "string", "description": "3-letter target currency (e.g. USD)"}
        },
        "required": ["source_curr", "target_curr"]
    },
    func=get_exchange_rate
)

# Simulate LLM Emitting a Tool Call Payload
simulated_model_call = json.dumps({
    "name": "calculate_mortgage",
    "arguments": {
        "principal": 350000,
        "rate": 4.5,
        "years": 25
    }
})

print("1. Simulated Model Output (Emitted JSON Tool Call):")
print(simulated_model_call)

# Dispatch and Execute in Client Runtime
execution_response = engine.validate_and_execute(simulated_model_call)
print("\n2. Runtime Tool Execution Result:")
print(json.dumps(execution_response, indent=2))

# Continuation message injected back to LLM
tool_role_message = {
    "role": "tool",
    "name": "calculate_mortgage",
    "content": json.dumps(execution_response)
}
print("\n3. Formatted Message Injected Back to Model History:")
print(json.dumps(tool_role_message, indent=2))

Common pitfalls

  • Ambiguous tool descriptions: If tool descriptions are vague (e.g. 'searches for stuff'), the model will misidentify when to invoke the tool. Descriptions must clearly state intent, preconditions, and return format.
  • Unsandboxed code execution: Executing code emitted by an LLM without strict containerisation (e.g. Docker, gVisor, WebAssembly) introduces catastrophic security vulnerabilities (arbitrary command execution). Always sandbox tool runners.
  • Failing to feed tool error messages back to the model: If an API throws a 400 Bad Request and your client simply crashes, the agent fails. Feeding the error message back as a tool response allows the model to self-correct its parameters.
  • Infinite tool-calling loops: If a tool repeatedly fails or returns empty results, an agent may loop indefinitely calling the same tool. Always enforce a hard ceiling on maximum sequential tool calls (e.g. max 5 iterations).

06 Check yourself

Q1Why are external tools and function calling necessary for Large Language Models?

Why: Language models are frozen in static weights and lack calculators, real-time data access, and execution engines. Function calling allows the model to act as a reasoning orchestrator, delegating math, retrieval, and actions to verified tools.

Q2In standard function calling architectures, where does the actual tool execution occur?

Why: The neural model only generates text representing the function name and JSON arguments. The host client application receives this payload, executes the actual code/API in a sandboxed runtime, and returns the result to the model.

Q3How should a robust agentic tool-calling system handle runtime exceptions (such as an API returning a 400 Bad Request)?

Why: Feeding structured error messages back to the model context turns errors into informative feedback. The model can diagnose missing parameters, incorrect types, or invalid formats and generate a corrected tool call.
