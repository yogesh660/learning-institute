Inference: KV cache, batching, paged attention

Autoregressive language model generation is fundamentally memory-bandwidth bound during token-by-token generation. To eliminate the quadratic O(N^2) computation incurred by re-evaluating past token states at every generation step, the Key-Value (KV) cache stores previously computed key and value activation tensors in high-bandwidth GPU memory (HBM). However, naive static memory pre-allocation for the KV cache introduces extreme internal and external memory fragmentation (wasting 60-80% of GPU memory). PagedAttention overcomes this limitation by partitioning KV caches into fixed-size physical memory pages, enabling non-contiguous storage, dynamic allocation, copy-on-write memory sharing across parallel generation paths, and high-throughput continuous batching.

01 The idea

Why does generating a 500-token response from an LLM feel so slow compared to processing a 500-token prompt, and why does an inference server with 80 GB of GPU memory run out of memory serving only a few dozen concurrent users? The answer lies in the asymmetric physics of transformer inference: prefill is compute-bound, but token-by-token decoding is memory-bandwidth bound and memory-capacity constrained by the Key-Value (KV) cache. Mastering the KV cache, iteration-level continuous batching, and virtual memory paging via PagedAttention is the key to achieving 10x-20x higher serving throughput.

The Quadratic Cost of Naive Generation: In autoregressive generation, generating token t+1 requires computing attention over all preceding tokens 1, ..., t. Without caching, the transformer must re-embed, project, and transform all previous t tokens through every attention layer, turning an N-token generation into an O(N^2) matrix recomputation nightmare.

The KV Cache Solution: In causal self-attention, token t attends only to tokens <= t. When decoding token t+1, the key and value representations of earlier tokens 1, ..., t do not change! By caching these K and V tensors in GPU memory, step t+1 only needs to compute q_{t+1}, k_{t+1}, v_{t+1} for the single new token, append (k_{t+1}, v_{t+1}) to the cache, and compute attention in O(N) linear time.

The Memory Crisis and Fragmentation: While the KV cache saves vast computation, it consumes enormous GPU memory. For a 13B model in FP16 with 40 layers, 40 heads, and head dimension 128, each token requires 2 * 2 * 40 * 5120 = 800 KB per request! Naive serving systems pre-allocate a contiguous memory buffer for each request's maximum context length (e.g. 4096 tokens = 3.2 GB). Because actual output lengths vary unpredictably, 60% to 80% of GPU memory sits idle in reserved, unused buffers.

PagedAttention: Virtual Memory for LLMs: Inspired by classical OS virtual memory paging, PagedAttention (Kwon et al., vLLM) partitions the KV cache of each sequence into small, fixed-size blocks (e.g. 16 tokens per block). Blocks do not need to be contiguous in physical GPU memory. A logical-to-physical block table dynamically allocates blocks on-demand, reducing wasted memory to under 4% and enabling shared memory across parallel beams and multi-turn prompt prefixes.

In everyday terms

Imagine writing a 500-page historical novel in a notebook. Without a KV cache, every time you want to write a new sentence on page 300, you are legally required to re-read and re-transcribe pages 1 through 299 from scratch before writing the new word. The KV cache is your bookmark: you keep all 299 previous pages open and simply append the new sentence. But how do you store your notebook? Naive serving is like buying a massive 2000-page binder for every client who walks through the door, even if they only plan to write a one-page postcard, quickly filling your bookshelf. PagedAttention is a binder with loose-leaf sheets: you allocate blank sheets one at a time only when a page fills up, allowing dozens of authors to share the same bookshelf without wasting empty paper.

03 The maths

  1. KV Cache Memory Footprint per Token

    M_{\text{token}} = 2 \times 2 \times n_{\text{layers}} \times n_{\text{kv\_heads}} \times d_{\text{head}} \times b_{\text{elem}} \quad \text{bytes}

    The factor of 2 accounts for storing both Key and Value tensors, and another factor of 2 represents 16-bit floating point precision (FP16/BF16, b_{\text{elem}} = 2 bytes). In Multi-Head Attention (MHA), n_{\text{kv\_heads}} = n_{\text{heads}}, while in Grouped-Query Attention (GQA), n_{\text{kv\_heads}} \ll n_{\text{heads}}, dramatically reducing memory requirements.

  2. Causal Attention Decoding with KV Cache

    \mathbf{a}_t = \text{Softmax}\left(\frac{\mathbf{q}_t \mathbf{K}_{\le t}^\top}{\sqrt{d_{\text{head}}}}\right) \mathbf{V}_{\le t}, \quad \text{where } \mathbf{K}_{\le t} = [\mathbf{K}_{

    During decoding at step t, query \mathbf{q}_t has dimension (1, d). Keys \mathbf{K}_{\le t} and values \mathbf{V}_{\le t} have dimension (t, d). The computational complexity of the attention step is O(t \cdot d), compared to O(t^2 \cdot d) if all past tokens had to be re-projected from scratch.

  3. PagedAttention Logical-to-Physical Mapping

    \text{block\_id} = \text{BlockTable}[r]\left[\left\lfloor \frac{i}{B} \right\rfloor\right], \quad \text{offset} = i \pmod B

    For request r at logical token position i, the physical memory location of the key or value vector is resolved by looking up the logical block index \lfloor i / B \rfloor in the sequence's block table, where B is the block size (e.g. 16). Physical blocks reside non-contiguously in GPU HBM.

04 Key takeaways

  • Autoregressive generation without a KV cache recomputes all past token keys and values, suffering from quadratic O(N^2) complexity.
  • The KV cache stores key and value activations across attention layers, reducing incremental per-token decoding computation to O(N).
  • Static memory allocation causes severe fragmentation, wasting 60-80% of GPU memory on reserved but unused output buffers.
  • PagedAttention resolves fragmentation by managing KV memory as virtual pages, enabling dynamic allocation, zero-waste block sharing, and high-throughput continuous batching.

05 In code

python
"""
KV Cache and PagedAttention Block Manager Simulation
Demonstrates autoregressive decoding with KV caching, memory calculation,
and non-contiguous physical block allocation.
"""

import math
from typing import List, Dict, Tuple, Optional

class SimpleKVCache:
    """Standard contiguous KV Cache for a single sequence."""
    def __init__(self, num_layers: int, num_heads: int, head_dim: int):
        self.num_layers = num_layers
        self.num_heads = num_heads
        self.head_dim = head_dim
        # Stores keys and values per layer: [layer_idx][token_idx] -> vector
        self.k_cache: List[List[List[float]]] = [[] for _ in range(num_layers)]
        self.v_cache: List[List[List[float]]] = [[] for _ in range(num_layers)]

    def append(self, layer: int, k_vec: List[float], v_vec: List[float]):
        self.k_cache[layer].append(k_vec)
        self.v_cache[layer].append(v_vec)

    def get_length(self, layer: int = 0) -> int:
        return len(self.k_cache[layer])

    def memory_bytes(self, bytes_per_elem: int = 2) -> int:
        tokens = self.get_length(0)
        # 2 (Key + Value) * num_layers * num_heads * head_dim * bytes_per_elem
        return 2 * tokens * self.num_layers * self.num_heads * self.head_dim * bytes_per_elem

class PagedBlockManager:
    """
    PagedAttention Block Manager
    Allocates fixed-size physical blocks and maintains per-sequence block tables.
    """
    def __init__(self, total_physical_blocks: int, block_size: int = 16):
        self.block_size = block_size
        self.free_blocks: List[int] = list(range(total_physical_blocks))
        # Maps request_id -> List[physical_block_id]
        self.block_tables: Dict[str, List[int]] = {}
        # Tracks token count per request
        self.seq_lengths: Dict[str, int] = {}

    def allocate_request(self, request_id: str, prompt_tokens: int):
        """Allocate initial physical blocks required for prompt."""
        num_blocks_needed = math.ceil(prompt_tokens / self.block_size)
        if len(self.free_blocks) < num_blocks_needed:
            raise MemoryError(f"Out of GPU Memory! Needed {num_blocks_needed} blocks, available {len(self.free_blocks)}.")

        allocated = [self.free_blocks.pop(0) for _ in range(num_blocks_needed)]
        self.block_tables[request_id] = allocated
        self.seq_lengths[request_id] = prompt_tokens

    def append_token(self, request_id: str) -> Tuple[int, int]:
        """
        Append a generated token to request. Allocates new physical block if current block is full.
        Returns (physical_block_id, offset_within_block).
        """
        curr_len = self.seq_lengths[request_id]
        block_idx = curr_len // self.block_size
        offset = curr_len % self.block_size

        if offset == 0:
            # Need a new physical block!
            if not self.free_blocks:
                raise MemoryError("Out of GPU Memory during token generation!")
            new_block = self.free_blocks.pop(0)
            self.block_tables[request_id].append(new_block)

        physical_block = self.block_tables[request_id][-1]
        self.seq_lengths[request_id] += 1
        return physical_block, offset

    def free_request(self, request_id: str):
        """Release allocated blocks back to the free pool."""
        if request_id in self.block_tables:
            self.free_blocks.extend(self.block_tables[request_id])
            del self.block_tables[request_id]
            del self.seq_lengths[request_id]

    def get_memory_utilisation(self, total_blocks: int) -> float:
        used_blocks = total_blocks - len(self.free_blocks)
        return round((used_blocks / total_blocks) * 100, 1)

# --- Demonstration Run ---
print("=== 1. KV Cache Memory Scaling Profile ===")
layers, heads, head_dim = 32, 32, 128  # Typical 7B parameter model
kv_cache = SimpleKVCache(layers, heads, head_dim)

# Simulate generating 512 tokens
for t in range(512):
    dummy_k = [0.1] * head_dim
    dummy_v = [0.2] * head_dim
    for l in range(layers):
        kv_cache.append(l, dummy_k, dummy_v)

mem_mb = kv_cache.memory_bytes() / (1024 * 1024)
print(f"Model: 7B (32 layers, 32 heads, dim {head_dim})")
print(f"Tokens in cache: {kv_cache.get_length()}")
print(f"KV Cache memory consumption: {mem_mb:.2f} MB per request")
print(f"Memory for 100 concurrent requests: {(mem_mb * 100) / 1024:.2f} GB\n")

print("=== 2. PagedAttention Dynamic Block Allocation ===")
total_blocks = 20
block_size = 4  # 4 tokens per block for demonstration
manager = PagedBlockManager(total_physical_blocks=total_blocks, block_size=block_size)

# Request A arrives with 6 tokens
manager.allocate_request("Req-A", prompt_tokens=6)
print(f"Req-A (6 prompt tokens) allocated physical blocks: {manager.block_tables['Req-A']}")

# Request B arrives with 4 tokens
manager.allocate_request("Req-B", prompt_tokens=4)
print(f"Req-B (4 prompt tokens) allocated physical blocks: {manager.block_tables['Req-B']}")

# Generate 3 tokens for Req-A
print("\n--- Generating 3 tokens for Req-A ---")
for step in range(1, 4):
    p_block, offset = manager.append_token("Req-A")
    print(f"  Step {step}: Token written to Physical Block {p_block}, offset {offset}")

print(f"Req-A updated block table: {manager.block_tables['Req-A']}")
print(f"GPU Block Memory Utilisation: {manager.get_memory_utilisation(total_blocks)}%")

# Free Req-B
manager.free_request("Req-B")
print(f"\nAfter freeing Req-B, available free blocks: {len(manager.free_blocks)}")

Common pitfalls

  • Ignoring KV cache growth when calculating serving capacity: A server with ample memory for model weights will rapidly crash with Out-Of-Memory (OOM) errors as concurrent sequence lengths grow.
  • Using static request batching instead of continuous batching: In static batching, short requests remain trapped in GPU memory until the longest request in the batch finishes generating.
  • Overlooking Grouped-Query Attention (GQA): For large context models, multi-head attention KV caches can exceed the model weights themselves; GQA reduces KV cache size by 4x to 8x.

06 Check yourself

Q1Why does autoregressive transformer decoding require a Key-Value (KV) cache?

Why: In causal decoder models, tokens only attend to past tokens. The key and value projections of past tokens do not change when a new token is generated. Caching them avoids recomputing the entire sequence at each step.

Q2What major problem does PagedAttention solve in production LLM serving?

Why: Traditional systems pre-allocated contiguous memory for the maximum possible sequence length, wasting up to 80% of GPU memory. PagedAttention allocates small fixed-size physical blocks on demand, eliminating internal fragmentation.

Q3How does continuous (iteration-level) batching differ from traditional request-level batching?

Why: Traditional batching holds GPU resources until the slowest request in the batch completes. Continuous batching schedules at the iteration level, inserting new requests as soon as any active request generates an end-of-sequence token.
