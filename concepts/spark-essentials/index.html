01 The idea

Single-node Python tools like pandas and NumPy are constrained by the RAM of a single physical machine. When datasets expand beyond dozens of gigabytes into terabyte scales, single-node processes crash with out-of-memory errors. Apache Spark provides distributed computing across clusters of worker machines, executing complex SQL queries, feature transformations, and matrix operations in parallel with resilient fault tolerance.

Spark's architecture follows a Driver-Executor master-worker topology. The Driver node contains the central coordination process, compiling user code into execution stages. Worker nodes run Executors—JVM processes that store partition data in RAM and execute parallel tasks.

Spark operations are strictly divided into Transformations (e.g. `select`, `filter`, `groupBy`, `join`) and Actions (e.g. `count`, `collect`, `write`). Transformations are lazily evaluated: Spark records transformations as a logical plan without executing them until an Action is explicitly triggered.

Lazy evaluation enables the Catalyst Optimiser to inspect the complete workflow end-to-end. Catalyst rearranges operators, pushes filters down to Parquet files (filter pushdown), eliminates dead columns (projection pruning), and selects optimal join strategies (broadcasting small tables to eliminate network shuffles).

The primary performance bottleneck in distributed computing is data shuffling: redistributing partitions across network cables during wide transformations (such as `groupBy` or `join`). Managing partition counts and leveraging broadcast joins prevents cluster network congestion and out-of-memory executor crashes.

In everyday terms

Imagine a team sorting and counting 10 million mail packages. If one worker tries to carry the entire warehouse of mail onto their desk at once, the desk collapses under the weight. Instead, a supervisor (Spark Driver) partitions the mail into 100 balanced carts and assigns each cart to a separate sorter (Spark Executor). If one sorter trips and drops their cart, only that single cart is reloaded and recounted, while the remaining 99 continue working uninterrupted.

02 Step by step

  1. Initialise SparkSession: Configure driver and executor RAM budgets and cluster manager endpoints.
  2. Load distributed data: Ingest Parquet, Delta Lake, or CSV partitions lazily into distributed DataFrames.
  3. Formulate declarative transformations: Apply filtering, aggregations, window functions, and string tokenisation using the PySpark DataFrame API.
  4. Inspect physical execution plan: Call `df.explain(True)` to review Catalyst optimisation, partition pruning, and broadcast join execution.
  5. Mitigate shuffle bottlenecks: For joins where one table is under 100MB, wrap the table in `broadcast()` to eliminate full network shuffles.
  6. Trigger terminal action: Execute an action (`write.parquet()` or `count()`) to trigger the physical DAG computation across the cluster.

03 The maths

  1. Distributed Partition Work Distribution

    T_{\mathrm{exec}} = \max_{k \in \{1, \dots, P\}} \left( \frac{\operatorname{Vol}(p_k)}{\mathrm{Throughput}_k} \right) + T_{\mathrm{shuffle}}

    Total job execution time is bounded by the slowest, largest partition (the straggler) plus network shuffle latency $T_{\mathrm{shuffle}}$.

  2. Broadcast Hash Join Communication Cost

    \operatorname{Comm}_{\mathrm{broadcast}} = O(N_{\mathrm{small}} \cdot K_{\mathrm{executors}}) \ll \operatorname{Comm}_{\mathrm{shuffle}} = O(N_{\mathrm{large}} + N_{\mathrm{small}})

    Broadcasting small table $N_{\mathrm{small}}$ avoids shuffling massive dataset $N_{\mathrm{large}}$ across the network, reducing network I/O by orders of magnitude.

  3. Catalyst Relational Algebra Equivalence

    \sigma_{\mathrm{cond}}(\pi_{\mathcal{A}}(R)) \equiv \pi_{\mathcal{A}}(\sigma_{\mathrm{cond}}(R))

    Catalyst pushes relational filter selection $\sigma$ prior to column projection $\pi$ to minimise intermediate data volumes in memory.

04 Key takeaways

  • Apache Spark scales data processing across distributed clusters with master-worker topology.
  • Transformations are lazily evaluated, allowing the Catalyst Optimiser to construct optimal physical execution plans.
  • Network shuffles during wide operations (`groupBy`, `join`) represent the primary performance bottleneck.
  • Broadcast joins copy small lookup tables to every worker, eliminating expensive full-cluster data shuffling.

05 In code

python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

# Initialise local SparkSession
spark = SparkSession.builder \
    .appName("MLFeatureEngineering") \
    .master("local[2]") \
    .config("spark.sql.shuffle.partitions", "4") \
    .getOrCreate()

# Create sample distributed dataset
data = [
    ("usr_1", "electronics", 250.0, "2026-04-01"),
    ("usr_2", "books", 15.0, "2026-04-01"),
    ("usr_1", "electronics", 80.0, "2026-04-02"),
    ("usr_3", "home", 450.0, "2026-04-02"),
    ("usr_2", "fashion", 60.0, "2026-04-03"),
]
columns = ["user_id", "category", "spend", "event_date"]
df = spark.createDataFrame(data, columns)

# Perform distributed lazy transformations
user_aggregates = df.filter(F.col("spend") > 20.0) \
    .groupBy("user_id") \
    .agg(
        F.sum("spend").alias("total_spend"),
        F.count("category").alias("transaction_count"),
        F.avg("spend").alias("avg_spend")
    )

# Inspect Catalyst execution plan
user_aggregates.explain()

# Trigger Action (collect results back to Driver)
results = user_aggregates.collect()
for row in results:
    print(f"User: {row['user_id']} | Total: £{row['total_spend']:.2f} | Count: {row['transaction_count']}")

spark.stop()

Common pitfalls

  • Data skew: If 90% of user records belong to a single "guest" ID, one executor processes almost the entire dataset while others sit idle (the straggler problem).
  • Calling `.collect()` on massive DataFrames: Calling `collect()` pulls all distributed data into the Driver node's local RAM, instantly crashing the Driver with an Out-of-Memory error.
  • Uncontrolled partitioning: Creating too few partitions under-utilises CPU cores; creating millions of tiny partitions creates excessive task scheduling overhead.

06 Check yourself

Q1Why are transformations in Apache Spark (like `.filter()` or `.select()`) lazily evaluated?

Why: Lazy evaluation lets the Catalyst query planner optimise the global execution graph—pushing filters down and pruning unused columns before touching disk.

Q2What is a "Broadcast Hash Join" in Apache Spark?

Why: Broadcast joins distribute the entire small table to every node. Each node can then join its local partition of the massive table without any network shuffle.

Q3What catastrophic mistake occurs if an engineer runs `df.collect()` on a 5-terabyte distributed Spark DataFrame?

Why: `collect()` transmits all distributed partitions to the central Driver memory. If the data exceeds Driver RAM, the process crashes.
