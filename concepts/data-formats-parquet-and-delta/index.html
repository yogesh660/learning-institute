01 The idea

Storing big data in raw text formats like CSV or JSON is disastrous for production machine learning: text files consume huge storage, lack schema enforcement, require slow row-by-row parsing, and cannot be filtered without scanning the entire file. Columnar storage formats like Apache Parquet and transactional lakehouse layers like Delta Lake compress data by up to 90%, enable sub-second predicate pushdown filtering, and provide ACID reliability with time travel.

Row-oriented formats (CSV, JSON, traditional relational tables) store all features of row 1, then row 2, etc. This is optimal for transactional writes (OLTP), but inefficient for machine learning (OLAP), where an algorithm typically selects only 10 features out of 200 columns across 50,000,000 rows.

Columnar storage (Apache Parquet) stores data column by column. Because all values in a column share the exact same data type, specialised compression algorithms (Run-Length Encoding, Dictionary Encoding, Snappy, ZSTD) achieve massive compression ratios.

Parquet files embed rich metadata in file footers, recording minimum and maximum values for every column block (row group). When an SQL or Spark query filters `WHERE country = 'GB'`, the engine reads the metadata and skips entire multi-megabyte row groups without touching disk (Predicate Pushdown / Min-Max pruning).

Delta Lake sits atop Parquet, adding a JSON transaction log (`_delta_log/`). This brings ACID transaction guarantees to data lakes, preventing readers from seeing partially written files, supporting `MERGE` upserts, and enabling "Time Travel" to query historical table snapshots.

In everyday terms

Imagine a library cataloguing a million books. A row-oriented CSV is like storing the entire text of every book sequentially in a single giant paper roll: finding every book published in 1985 requires reading through every single word of all million books from start to finish. A columnar format is like an organized index where all publication years are listed in one compact column; you scan only that single column in seconds and ignore the rest.

02 Step by step

  1. Choose compression codec: Select Snappy for balanced speed/compression or ZSTD for archival storage and high-throughput network reads.
  2. Organise into row groups: Configure Parquet row group size (typically 128MB to 512MB) to balance memory usage during compression against parallel scan efficiency.
  3. Partition on low-cardinality keys: Partition directory trees on sensible query keys (e.g. `year=2026/month=04/`) while avoiding hive partition over-fragmentation.
  4. Leverage predicate pushdown: Write queries with explicit column filtering so engines skip non-matching row groups using min/max footer metadata.
  5. Enable Delta Lake ACID logging: Wrap Parquet tables with Delta Lake to guarantee atomic commits and prevent corrupted reads during pipeline crashes.
  6. Use Delta Time Travel for model training: Query historical tables via `VERSION AS OF` or `TIMESTAMP AS OF` to ensure absolute training set reproducibility.

03 The maths

  1. Columnar I/O Scan Reduction Ratio

    \mathrm{ScanRatio} = \frac{\sum_{j \in \mathcal{S}_{\mathrm{query}}} \mathrm{size}(C_j)}{\sum_{k=1}^D \mathrm{size}(C_k)} \ll 1.0

    When a model requires feature subset $\mathcal{S}_{\mathrm{query}}$, columnar storage reads strictly those columns, reducing disk I/O proportionally.

  2. Predicate Pushdown Pruning Condition

    \text{Skip Row Group if } \left( v_{\mathrm{target}} < \min(C_{j,g}) \;\lor\; v_{\mathrm{target}} > \max(C_{j,g}) \right)

    If the target query value falls outside the min-max boundary stored in row group header $g$, the entire chunk is bypassed without decompression.

  3. Delta Lake ACID Serialisability

    T_{\mathrm{commit}}(k) = \mathrm{AtomicWrite}(\text{\_delta\_log/}00000k.\mathrm{json})

    State transitions in Delta Lake are recorded through atomic commit logs, guaranteeing that concurrent readers always observe consistent snapshots.

04 Key takeaways

  • Parquet stores data column-by-column, enabling high compression ratios and partial column reads.
  • Predicate pushdown skips entire blocks of records using min/max statistics in file footers.
  • Delta Lake adds an ACID transaction log to Parquet, preventing dirty reads and corrupted writes.
  • Delta Time Travel enables querying historical snapshots for reproducible model training.

05 In code

python
import pandas as pd
import numpy as np
import os

# Create synthetic dataset with diverse column types
N = 100_000
df = pd.DataFrame({
    'user_id': [f"usr_{i:06d}" for i in range(N)],
    'category': np.random.choice(['electronics', 'books', 'fashion', 'home'], size=N),
    'amount': np.random.exponential(scale=50.0, size=N),
    'is_fraud': np.random.choice([0, 1], size=N, p=[0.99, 0.01])
})

# 1. Save as uncompressed CSV
csv_path = 'sample_data.csv'
df.to_csv(csv_path, index=False)
csv_size_mb = os.path.getsize(csv_path) / (1024 * 1024)

# 2. Save as columnar Parquet with Snappy compression
parquet_path = 'sample_data.parquet'
df.to_parquet(parquet_path, engine='pyarrow', compression='snappy')
parquet_size_mb = os.path.getsize(parquet_path) / (1024 * 1024)

print(f"CSV File Size:     {csv_size_mb:.2f} MB")
print(f"Parquet File Size: {parquet_size_mb:.2f} MB")
print(f"Storage Reduction: {(1.0 - parquet_size_mb / csv_size_mb) * 100:.1f}% space saved!")

# Clean up temp files
os.remove(csv_path)
os.remove(parquet_path)

Common pitfalls

  • The "Small Files Problem": Writing thousands of tiny 50KB Parquet files overwhelms storage metadata and degrades query speed; compact files into 128MB–1GB sizes.
  • Over-partitioning: Partitioning tables by high-cardinality keys (like user ID or timestamp) creates millions of empty folders; partition only by coarse keys (year, month).
  • Ignoring column projection: Running `SELECT *` defeats the entire efficiency advantage of columnar formats by forcing disk reads of all columns.

06 Check yourself

Q1Why does Apache Parquet achieve significantly higher compression ratios than CSV or JSON formats?

Why: Contiguous values of identical types exhibit low entropy and repeated patterns, allowing columnar encoders (Snappy, ZSTD, Dictionary encoding) to compress tightly.

Q2What is "predicate pushdown" in columnar query engines like Spark and DuckDB?

Why: Predicate pushdown evaluates filter conditions against file block metadata. If a row group's maximum value is less than the filter value, the engine skips the block entirely.

Q3What critical capability does Delta Lake's transaction log (`_delta_log/`) provide for machine learning pipelines?

Why: Delta Lake's transaction log enables ACID guarantees and time-travel querying, ensuring datasets are not corrupted by partial writes and historical states can be reproduced exactly.
