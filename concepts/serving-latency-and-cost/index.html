Serving, latency and cost

Deploying Large Language Models in production requires navigating the trade-offs between user-perceived responsiveness and hardware operational cost. LLM serving latency is partitioned into two distinct phases: Time to First Token (TTFT), dominated by the compute-bound prompt prefill phase; and Time Per Output Token (TPOT / inter-token latency), dominated by the memory-bandwidth-bound autoregressive decoding phase. By analysing the GPU Roofline Model, engineers can determine whether workloads are memory-bound or compute-bound, optimise continuous batching and prompt caching, and calculate total cost of ownership (TCO) per million generated tokens.

01 The idea

When a user types a prompt into a conversational AI, why is the initial delay noticeably longer than the steady flow of incoming words, and why does serving cost explode as prompt lengths increase? Serving LLMs efficiently requires balancing user experience metrics (latency) against financial constraints (GPU capital depreciation and operational cost). Understanding the physics of TTFT, TPOT, arithmetic intensity, and token economics is fundamental to architecting scalable LLM systems.

Prefill vs Decode: The Two Physics Regimes: - Prefill Phase: The model ingests the entire prompt at once. Because all tokens are known simultaneously, matrix multiplications are large, parallel, and compute-bound (high arithmetic intensity, saturating GPU tensor cores). - Decode Phase: The model generates one token at a time autoregressively. Each step loads the entire model weight matrix (e.g. 14 GB for a 7B FP16 model) into processor registers to compute arithmetic on just a single token vector. Decoding is strictly memory-bandwidth bound.

The Core Latency Metrics: - TTFT (Time to First Token): Time from request submission until the first token streams back. Governed by prompt length, queuing delay, and prefill throughput. - TPOT (Time Per Output Token): Average duration between successive generated tokens (inter-token latency). Governed by memory bandwidth and active batch size. - Total Latency: TTFT + (N_{out} - 1) * TPOT.

The Roofline Model for Serving: Arithmetic intensity measures operations per byte loaded (FLOPs/Byte). If a GPU has a memory bandwidth of 2.0 TB/s and compute capacity of 312 TFLOPs, any workload with an arithmetic intensity below 156 FLOPs/Byte is memory-bandwidth bound. Batching multiple requests increases arithmetic intensity because the same loaded model weights are reused across multiple concurrent queries.

Prompt Caching and Economics: In conversational agents and RAG systems, large system prompts and document contexts are repeated across turns. Prompt caching saves precomputed KV caches across requests, dropping TTFT by up to 90% and cutting inference costs dramatically.

In everyday terms

Think of an express delivery service. The Prefill phase is loading a freight truck with a huge shipment of goods from a warehouse (compute-intensive, massive bulk operation done all at once). The Decode phase is the delivery courier visiting individual houses one by one to drop off a single letter at each doorstep (memory-bandwidth bound, where the travelling vehicle spends almost all its time driving rather than unloading). If the courier delivers letters for ten houses on the same street at once (batching), the trip is ten times more efficient than making ten separate round trips.

03 The maths

  1. Decode Phase Arithmetic Intensity and Memory Bandwidth Bound

    I_{\text{decode}} = \frac{2 \cdot P \cdot B}{2 \cdot P + \text{KV}_{\text{bytes}}(B)} \approx B \quad \left[\frac{\text{FLOPs}}{\text{Byte}}\right]

    For a model with P parameters and batch size B, generating 1 token performs 2 \cdot P \cdot B floating point operations while loading 2 \cdot P bytes of model weights (assuming 16-bit precision). For batch size B=1, arithmetic intensity is approximately 1 FLOP/byte—vastly below modern GPU tensor saturation thresholds (150-300 FLOPs/byte).

  2. Time Per Output Token (TPOT) Lower Bound

    \text{TPOT}_{\min}(B) = \max\left( \frac{2 \cdot P \text{ bytes}}{\text{BW}_{\text{mem}}}, \, \frac{2 \cdot P \cdot B \text{ FLOPs}}{\text{Peak}_{\text{compute}}} \right) \div B

    When batch size B is small, decoding is memory-bandwidth bound and per-token latency is dictated by total model weight size divided by memory bandwidth \text{BW}_{\text{mem}}. As batch size grows, computation saturates peak tensor compute capacity \text{Peak}_{\text{compute}}.

  3. Serving Cost per Million Generated Tokens

    \text{Cost}_{1\text{M}} = \frac{\text{Hourly GPU Cost (\$/h)}}{3600 \times \text{Throughput (Tokens/s)}} \times 10^6

    System cost efficiency is directly proportional to sustained generation throughput. Maximising continuous batching and utilizing prompt caching directly scales throughput, reducing cost per million tokens.

04 Key takeaways

  • LLM serving operates across two distinct hardware regimes: compute-bound prompt prefill and memory-bandwidth-bound token decoding.
  • Time to First Token (TTFT) measures user-perceived responsiveness to prompt submission; Time Per Output Token (TPOT) measures streaming speed.
  • At batch size 1, decoding has an arithmetic intensity of ~1 FLOP/byte, severely underutilising GPU tensor cores; batching increases arithmetic intensity toward hardware saturation.
  • Serving cost economics depend directly on aggregate token throughput; continuous batching and prompt caching dramatically reduce cost per million tokens.

05 In code

python
"""
LLM Serving Latency and Cost Profiler
Calculates TTFT, TPOT, Roofline Arithmetic Intensity,
and Dollar Cost per Million Tokens across GPU specifications.
"""

from typing import Dict, Any

class GPUSpec:
    def __init__(self, name: str, peak_tflops_fp16: float, mem_bandwidth_tb_s: float, mem_gb: float, hourly_cost: float):
        self.name = name
        self.peak_flops = peak_tflops_fp16 * 1e12
        self.mem_bandwidth = mem_bandwidth_tb_s * 1e12
        self.mem_gb = mem_gb
        self.hourly_cost = hourly_cost
        # Hardware balance knee point (FLOPs/Byte)
        self.balance_point = self.peak_flops / self.mem_bandwidth

class LLMServingProfiler:
    def __init__(self, model_params_billions: float, gpu: GPUSpec):
        self.params = model_params_billions * 1e9
        self.gpu = gpu
        # Weight bytes in FP16 (2 bytes per param)
        self.weight_bytes = self.params * 2

    def profile_latency(self, prompt_tokens: int, output_tokens: int, batch_size: int = 1) -> Dict[str, Any]:
        """Compute TTFT, TPOT, and total latency under Roofline Model."""
        # 1. Prefill Phase (Compute-bound parallel forward pass)
        prefill_flops = 2 * self.params * prompt_tokens * batch_size
        prefill_time = prefill_flops / self.gpu.peak_flops
        # TTFT includes prefill plus initial memory load overhead
        ttft_seconds = prefill_time + (self.weight_bytes / self.gpu.mem_bandwidth)

        # 2. Decode Phase (Memory-bandwidth bound token generation)
        decode_flops_per_step = 2 * self.params * batch_size
        decode_time_mem = self.weight_bytes / self.gpu.mem_bandwidth
        decode_time_compute = decode_flops_per_step / self.gpu.peak_flops
        step_time = max(decode_time_mem, decode_time_compute)
        
        tpot_seconds = step_time / batch_size  # Effective inter-token time per request
        total_decode_time = (output_tokens - 1) * step_time
        total_latency = ttft_seconds + total_decode_time

        # 3. Arithmetic Intensity (FLOPs per byte)
        arithmetic_intensity = decode_flops_per_step / self.weight_bytes

        return {
            "ttft_ms": round(ttft_seconds * 1000, 2),
            "tpot_ms": round(tpot_seconds * 1000, 2),
            "total_latency_s": round(total_latency, 2),
            "arithmetic_intensity": round(arithmetic_intensity, 2),
            "is_memory_bound": arithmetic_intensity < self.gpu.balance_point,
            "tokens_per_second_per_stream": round(1.0 / tpot_seconds, 1),
            "aggregate_tokens_per_second": round(batch_size / step_time, 1),
        }

    def compute_cost_per_million_tokens(self, aggregate_throughput_tok_s: float) -> float:
        """Calculate dollar cost per 1M tokens based on sustained throughput."""
        tokens_per_hour = aggregate_throughput_tok_s * 3600
        cost_per_token = self.gpu.hourly_cost / tokens_per_hour
        return round(cost_per_token * 1e6, 3)

# --- Demonstration Profile ---
a100 = GPUSpec(name="NVIDIA A100 SXM 80GB", peak_tflops_fp16=312, mem_bandwidth_tb_s=2.0, mem_gb=80, hourly_cost=2.50)
profiler = LLMServingProfiler(model_params_billions=7.0, gpu=a100)

print(f"=== GPU Hardware Specifications: {a100.name} ===")
print(f"Peak Compute: 312 TFLOPs | Memory Bandwidth: 2.0 TB/s")
print(f"Hardware Balance Point (Roofline Knee): {a100.balance_point:.1f} FLOPs/Byte\n")

print("=== Latency Profile for 7B Model (Prompt: 512 tokens, Output: 128 tokens) ===")
for batch in [1, 4, 16, 64]:
    stats = profiler.profile_latency(prompt_tokens=512, output_tokens=128, batch_size=batch)
    cost_1m = profiler.compute_cost_per_million_tokens(stats["aggregate_tokens_per_second"])
    regime = "MEMORY-BOUND" if stats["is_memory_bound"] else "COMPUTE-BOUND"
    print(f"Batch Size {batch:2d}:")
    print(f"  TTFT: {stats['ttft_ms']} ms | TPOT: {stats['tpot_ms']} ms | Intensity: {stats['arithmetic_intensity']} FLOPs/B [{regime}]")
    print(f"  Aggregate Throughput: {stats['aggregate_tokens_per_second']} tok/s | Cost: \${cost_1m:.3f} per 1M tokens")

Common pitfalls

  • Sizing hardware based purely on TFLOPs: For interactive decoding, memory bandwidth (TB/s) is the primary determinant of latency, not peak FLOPs.
  • Ignoring the impact of prompt length on TTFT: Massive prompt contexts consume significant prefill compute and delay first-token delivery; prompt caching is crucial for repeated context.
  • Optimising only for throughput at the expense of latency: Large static batches maximise throughput but create intolerable TPOT spikes for interactive end-users.

06 Check yourself

Q1Why is single-request autoregressive token decoding memory-bandwidth bound rather than compute bound?

Why: At batch size 1, generating 1 token requires reading all model weights from HBM (e.g. 14 GB for a 7B FP16 model) to perform arithmetic on just one token vector, yielding an arithmetic intensity of ~1 FLOP/byte.

Q2What does Time to First Token (TTFT) primarily measure in conversational AI?

Why: TTFT captures the initial response latency, evaluating how quickly the server processes the full prompt context and generates the initial output token.

Q3How does prompt caching reduce both latency and operational serving costs?

Why: In multi-turn chat and RAG, large system prompts and reference texts are repeated. Prompt caching reuses already computed Key and Value tensors, dropping prefill latency and computational expense.
