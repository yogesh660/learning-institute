Distributed Deep Learning: Distributed Data Parallel (DDP) and Fully Sharded Data Parallel (FSDP)

Scaling model training across multiple GPUs and nodes using Ring-AllReduce DDP and parameter/gradient/optimiser sharding with FSDP (ZeRO).

01 The idea

Modern deep learning models have expanded beyond the compute and memory limits of any single GPU. A 70-billion parameter LLM requires over 140 GB of RAM just to store 16-bit weights—before accounting for gradients and optimiser states, which require another 560 GB. Scaling training across dozens or thousands of GPUs requires distributed parallelism: Distributed Data Parallel (DDP) scales throughput for models that fit in one GPU, while Fully Sharded Data Parallel (FSDP) shards models across GPU memories.

Single-GPU training is constrained by three memory consumers: Model Parameters, Gradients, and Optimiser States (in AdamW, 2 states per parameter: momentum $m$ and variance $v$, requiring $12$ bytes per parameter in mixed precision). Activations add further memory scaling with batch size.

Distributed Data Parallel (DDP) replicates the entire model on each GPU. Each GPU processes an independent minibatch slice, computes local gradients, and synchronises gradients across all GPUs using an efficient Ring-AllReduce collective communication algorithm before taking an identical optimiser step.

DDP fails when the model itself exceeds a single GPU's VRAM. ZeRO (Zero Redundancy Optimiser) and PyTorch FSDP (Fully Sharded Data Parallel) eliminate memory redundancy by sharding states across ranks: ZeRO-1 shards optimiser states (4x memory reduction), ZeRO-2 shards optimiser states and gradients (8x reduction), and ZeRO-3 / FSDP shards optimiser states, gradients, and model parameters.

In FSDP, during the forward pass, each layer's parameters are gathered via `AllGather` across ranks just in time for computation, and immediately discarded after the layer computes. Backward passes repeat this just-in-time gather and execute `ReduceScatter` to compute and shard gradients.

In everyday terms

Imagine transcribing an ancient 1,000-page manuscript. In DDP, each scribe receives an identical copy of the full dictionary (model weights) and transcribes a separate chapter (minibatch); at the end of each hour, all scribes shout out their edits and average their notes. In FSDP, the dictionary itself is so enormous that no scribe has room on their desk for it; each scribe holds 1/8th of the dictionary pages in their drawer, swapping pages on demand right when a word needs translating and immediately discarding it afterwards.

02 Step by step

  1. Evaluate model memory footprint: Compute total memory $M_{\mathrm{total}} = 16 \times N_{\mathrm{params}} + M_{\mathrm{activations}}$. If $M_{\mathrm{model}} \le V_{\mathrm{GPU}}$, select DDP; otherwise select FSDP.
  2. Initialise process group: Call `torch.distributed.init_process_group(backend="nccl")` using NVIDIA Collective Communications Library (NCCL).
  3. Wrap model: Wrap PyTorch module with `torch.nn.parallel.DistributedDataParallel(model)` or `FullyShardedDataParallel(model, auto_wrap_policy=...)`.
  4. Distribute data partitions: Attach a `DistributedSampler(dataset)` to the DataLoader to ensure each GPU receives a disjoint, non-overlapping batch slice.
  5. Set epoch seed in sampler: Call `sampler.set_epoch(epoch)` at the start of each epoch to shuffle batches uniquely across GPUs.
  6. Execute synchronized training step: Compute forward pass, backward pass (which triggers overlapping communication and computation), and optimiser step.

03 The maths

  1. Total Training Memory Overhead (AdamW FP16/FP32)

    M_{\mathrm{static}} = \underbrace{2 N}_{\text{FP16 Weights}} + \underbrace{2 N}_{\text{FP16 Grads}} + \underbrace{4 N}_{\text{FP32 Master Weights}} + \underbrace{8 N}_{\text{Adam } m, v} = 16 N \text{ bytes}

    Static memory overhead scales at 16 bytes per parameter, requiring 160GB for a 10-billion parameter model before activations.

  2. Ring-AllReduce Communication Volume

    \operatorname{Comm}_{\mathrm{AllReduce}} = 2 \cdot \left( \frac{K - 1}{K} \right) \cdot N_{\mathrm{bytes}}

    The communication volume per GPU in Ring-AllReduce is completely independent of the total GPU count $K$, scaling only with model byte size.

  3. FSDP (ZeRO-3) Memory per GPU Rank

    M_{\mathrm{FSDP}}(K) = \frac{16 N}{K} + M_{\mathrm{layer\_buffer}} + M_{\mathrm{activations}}

    Shards all parameters, gradients, and optimiser states across $K$ GPUs, scaling static memory linearly down with cluster size.

04 Key takeaways

  • DDP replicates the model on each GPU, synchronising gradients using Ring-AllReduce communication.
  • DDP communication volume is independent of the number of GPUs, scaling near-linearly with cluster size.
  • FSDP (ZeRO-3) shards parameters, gradients, and optimiser states, dividing static memory consumption by $K$ GPUs.
  • FSDP enables training models with tens of billions of parameters that cannot fit into single GPU VRAM.

Common pitfalls

  • Forgetting `sampler.set_epoch(epoch)`: If omitted, the DistributedSampler generates the exact same batch sequence on every epoch, degrading training stochasticity.
  • Using PyTorch DataParallel (`nn.DataParallel`): Single-process multi-threaded `DataParallel` suffers from Python GIL bottlenecks and master-GPU memory imbalance; always use DDP.
  • Communication overhead on slow interconnects: Running FSDP across nodes connected by standard 1Gbps Ethernet causes GPUs to spend 90% of their time waiting for network AllGather; high-speed InfiniBand (RoCE) is essential.

06 Check yourself

Q1Why is `DistributedDataParallel` (DDP) far superior to `DataParallel` (DP) in PyTorch?

Why: `DataParallel` runs in a single process subject to Python GIL locks and concentrates all gradient aggregation on GPU 0. DDP spawns separate processes with decentralized Ring-AllReduce.

Q2When must an engineer switch from standard DDP to FSDP (Fully Sharded Data Parallel)?

Why: DDP requires the full model to fit on every single GPU. When a model is too large for one GPU, FSDP shards parameters and states across multiple GPUs.

Q3What collective communication operation does DDP use to synchronize gradients across GPUs?

Why: Ring-AllReduce divides tensor buffers into chunks passed around a logical ring of nodes, achieving optimal network bandwidth utilization.
