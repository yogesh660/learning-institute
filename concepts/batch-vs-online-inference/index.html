01 The idea

Not all machine learning models belong behind a live HTTP endpoint. Batch inference scores millions of records offline on scheduled pipelines, maximising hardware throughput and amortising computational cost. Online inference generates predictions on-demand in milliseconds using live streaming features, delivering immediate personalisation at the cost of operational complexity. Selecting the right inference pattern—or combining them in a hybrid two-tower architecture—is a fundamental system design decision.

Consider two contrasting machine learning applications at a major retail bank. Application A computes weekly credit card churn risk scores for 10 million customers to trigger targeted retention emails. Nobody needs to know a customer's churn score in 20 milliseconds while they are browsing an app; computing scores every Sunday night in an offline batch job using high-throughput Spark or SQL clusters is cheap, robust, and cost-effective. Application B evaluates credit card transactions for fraud: when a customer taps their card at a terminal, the bank has 50 milliseconds to approve or decline the purchase. Computing fraud scores offline the night before is impossible because the transaction features (merchant, location, amount) did not exist until the card was tapped.

The choice between batch and online inference balances cost, latency, and feature freshness. Batch inference prioritises throughput and cost-efficiency: you can run heavy ensembles or compute complex aggregations (e.g. 90-day rolling spend) across full tables, writing precomputed predictions directly into a low-latency key-value cache (like Redis). The downside is staleness: predictions reflect data as of the last batch run. Online inference guarantees maximum freshness: predictions react instantly to a user's latest in-session clicks. However, online inference demands dedicated 24/7 server infrastructure, strict tail SLAs (sub-100ms response), and lightweight feature pipelines.

Modern high-scale recommendation engines (such as streaming platforms and e-commerce marketplaces) combine both paradigms into a hybrid two-tower pattern. Offline batch pipelines precompute candidate item embeddings for 10 million items every night. When a user opens the mobile app, a lightweight online scoring service retrieves the top 100 candidate items via approximate nearest neighbours and ranks them in real-time using current session context (time of day, device, and last 3 clicks).

In everyday terms

A bakery preparing bread: baking 500 loaves of sourdough in large ovens overnight (batch precomputation) versus custom-making a fresh hot espresso in 30 seconds when a customer orders at the counter (online inference).

02 Step by step

  1. Audit operational freshness requirements: determine whether the business decision requires data generated at query time or if hourly/daily batch data is sufficient.
  2. Establish latency and throughput budgets: benchmark target response times (e.g. batch: 10,000 items/sec over 2 hours; online: < 50ms per item with p99 < 100ms).
  3. Assess feature store dependencies: verify whether features reside offline in data warehouses (BigQuery, Snowflake) or require streaming feature stores (Redis, Feast) for sub-second retrieval.
  4. Evaluate cost economics: compare continuous 24/7 online server hosting costs against on-demand scheduled batch cluster compute.
  5. Design fallback mechanisms: implement local caching or rule-based fallback heuristics for online inference endpoints when network timeouts occur.

03 The maths

  1. Amortised hardware inference cost comparison

    C_{\text{batch}} = \frac{T_{\text{run}} \cdot P_{\text{compute}}}{N_{\text{total}}}, \qquad C_{\text{online}} = \frac{24 \times 3600 \cdot P_{\text{cluster}}}{N_{\text{requests}}}

    Where $P_{\text{compute}}$ and $P_{\text{cluster}}$ are hourly infrastructure costs. Because scheduled batch jobs achieve near 100% GPU/CPU utilization during execution, $C_{\text{batch}}$ is typically an order of magnitude cheaper per scored record than continuous online serving under variable traffic.

  2. End-to-end online serving latency budget

    T_{\text{total}} = T_{\text{network\_roundtrip}} + T_{\text{feature\_retrieval}} + T_{\text{inference}} + T_{\text{serialization}} \le T_{\text{SLA}}

    In online inference, model computation $T_{\text{inference}}$ is only one component of the total latency budget; network roundtrip and database feature hydration often dominate total response time.

  3. Feature freshness staleness function

    \Delta t_{\text{staleness}} = t_{\text{inference}} - t_{\text{feature\_observed}}

    In batch systems, $\Delta t$ can range from hours to days; in online streaming systems, $\Delta t \to 0$, maximising responsiveness to immediate user behavioural shifts.

04 Key takeaways

  • Batch inference maximises throughput and minimises hardware cost by scoring millions of records in scheduled offline pipelines.
  • Online inference is mandatory when features only exist at query time (such as fraud detection and search autocomplete).
  • Hybrid architectures precompute static candidate sets in batch, applying lightweight ranking online using real-time session context.

05 In code

python
import numpy as np
import time

np.random.seed(42)
n_samples, n_features = 1000, 10
X = np.random.normal(0, 1, size=(n_samples, n_features))
w = np.random.normal(0, 1, size=n_features)

# 1. Batch inference (vectorised matrix-vector product)
t0 = time.perf_counter()
preds_batch = 1.0 / (1.0 + np.exp(-np.dot(X, w)))
t_batch = time.perf_counter() - t0
throughput_batch = n_samples / t_batch

# 2. Online inference simulation (iterative per-request processing)
t0 = time.perf_counter()
preds_online = []
for i in range(n_samples):
    x_i = X[i]
    p_i = 1.0 / (1.0 + np.exp(-np.dot(x_i, w)))
    preds_online.append(p_i)
t_online = time.perf_counter() - t0
throughput_online = n_samples / t_online

print(f"Batch inference throughput:  {throughput_batch:,.0f} samples/sec (Total: {t_batch*1000:.2f}ms)")
print(f"Online inference throughput: {throughput_online:,.0f} samples/sec (Total: {t_online*1000:.2f}ms)")
print(f"Throughput speedup factor:   {throughput_batch / throughput_online:.1f}x")

Common pitfalls

  • Building an expensive online microservice when a daily scheduled batch job stored in Redis satisfies the business requirement.
  • Online feature hydration bottlenecks: designing a 5ms model that times out because retrieving user history from a remote SQL database takes 150ms.
  • Training-serving skew: using pandas transformations in offline batch training that differ subtly from Java/C++ streaming feature transformations in production online inference.

06 Check yourself

Q1When is online (real-time) inference strictly required over batch precomputation?

Why: Online inference is essential when features cannot be known in advance (such as a card transaction or search query). If features only appear at the moment of the request, batch precomputation is impossible.

Q2What is the primary economic advantage of batch inference over online inference?

Why: Batch jobs run on-demand clusters at near 100% capacity, scoring millions of rows at peak throughput and shutting down, whereas online serving requires 24/7 provisioned capacity sized for peak traffic.

Q3What is 'training-serving skew' in machine learning operations?

Why: Training-serving skew occurs when data pipelines differ between offline training (e.g. batch SQL/pandas) and online serving (e.g. streaming Java/C++ or microservices), causing silent prediction errors in production.
