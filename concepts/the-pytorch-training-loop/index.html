01 The idea

Unlike high-level frameworks that bury mechanics inside opaque black-box calls, PyTorch exposes the training loop explicitly. An idiomatic loop orchestrates data mini-batching, device transfers, gradient zeroing, forward propagation, loss calculation, backpropagation, and optimiser parameter updates with surgical precision.

Training a neural network is an iterative dialogue between empirical data batches and parameter gradients. At the centre of every training script sits a nested loop: an outer loop that repeats over epochs (full sweeps through the dataset) and an inner loop that processes one mini-batch at a time. Within each batch, five fundamental operations must execute in strict sequence: zero gradients, compute predictions, evaluate the loss, backpropagate gradients, and step the optimiser.

The first operation—zeroing gradients via `optimiser.zero_grad(set_to_none=True)`—is essential because PyTorch deliberately accumulates gradients by default. If you omit this call, gradients from the current batch add directly to the residual gradients of all preceding batches, quickly blowing parameters to non-finite infinity. Passing `set_to_none=True` deletes the gradient memory buffers entirely rather than writing zeros into them, saving valuable GPU memory bandwidth.

Equally crucial is the discipline of toggling execution modes. Setting `model.train()` enables stochastic behaviours such as dropout and updates running statistics in Batch Normalisation. Conversely, before running validation, switching to `model.eval()` freezes these layers and wrapping evaluation in `with torch.no_grad():` disables computational graph construction, drastically slashing memory consumption and preventing memory leaks.

In everyday terms

Like a competitive rowing crew executing a stroke cycle: clear the oars from the water (zero gradients), drive the stroke forward (forward pass), check boat speed against the pace clock (loss), assess blade resistance (backward pass), and adjust rower body angles (optimiser step).

02 Step by step

  1. Assemble the pipeline: define the neural architecture, instantiate the criterion (`nn.CrossEntropyLoss`), initialise the optimiser (torch.optim.AdamW), and prepare shuffled `DataLoader` instances.
  2. Set training mode: invoke `model.train()` at the start of each training epoch so dropout masks and normalisation layers engage their stochastic training logic.
  3. Execute the 5-step batch loop: iterate over mini-batches, clear parameter gradients, evaluate the forward pass, compute the loss scalar, run `loss.backward()`, and apply `optimiser.step()`.
  4. Accumulate metrics cleanly: extract scalar loss values using `loss.item()` rather than appending raw loss tensors, preventing dynamic computational graphs from accumulating indefinitely in GPU memory.
  5. Run evaluation under no-grad: switch to `model.eval()`, wrap validation loops in `with torch.no_grad():`, accumulate validation loss, and step learning-rate schedulers.

03 The maths

  1. Gradient accumulation across micro-batches

    $$g = \frac{1}{K}\sum_{k=1}^K \nabla_\theta \mathcal{L}(B_k; \theta), \qquad \theta \leftarrow \theta - \eta \cdot \Delta(g)$$

    $K$ is the number of accumulation steps, $B_k$ is the $k$-th micro-batch, and $\Delta(g)$ is the optimiser update direction. Because PyTorch accumulates gradients in `p.grad` by default, calling `optimiser.step()` and `optimiser.zero_grad()` only once every $K$ batches enables training with large effective batch sizes without exhausting GPU VRAM.

  2. Training vs evaluation forward transformation

    $$\hat{y}_{\text{train}} = f(x; \theta, \mathbf{m} \sim \operatorname{Bernoulli}(1-p), \mu_B, \sigma_B^2), \qquad \hat{y}_{\text{eval}} = f(x; \theta, \mathbf{1}, \mu_{\text{run}}, \sigma_{\text{run}}^2)$$

    Illustrates the operational difference between `model.train()` and `model.eval()`. In training mode, activations are perturbed by random dropout mask $\mathbf{m}$ and normalised by batch statistics $(\mu_B, \sigma_B^2)$; in evaluation mode, all units remain active ($\mathbf{1}$) and frozen population averages $(\mu_{\text{run}}, \sigma^2_{\text{run}})$ ensure deterministic inference.

04 Key takeaways

  • Calling `optimiser.zero_grad(set_to_none=True)` before `loss.backward()` is mandatory; omitting it causes gradients from consecutive batches to compound destructively.
  • Setting `model.eval()` adjusts layer behaviour (dropout, batchnorm) but does not turn off autodiff; `with torch.no_grad():` is required to disable computational graph allocation during evaluation.
  • Tracking total epoch loss must always use `loss.item()` (a Python float); adding the raw `loss` tensor retains the entire autograd tape in VRAM, causing an out-of-memory crash.

05 In code

python
import numpy as np

# Synthetic linear dataset: y = 2*x + 1
np.random.seed(42)
X = np.random.randn(20, 1)
y = 2.0 * X + 1.0 + np.random.randn(20, 1) * 0.05

# Initialise model parameters and learning rate
w = np.random.randn(1, 1)
b = np.zeros(1)
lr = 0.1

print("Executing 5-step training loop across 30 epochs:")
for epoch in range(1, 31):
    # Step 1: Zero gradients
    dw, db = np.zeros_like(w), np.zeros_like(b)
    # Step 2: Forward pass
    y_pred = X @ w + b
    # Step 3: Compute loss (Mean Squared Error)
    loss = float(np.mean((y_pred - y)**2))
    # Step 4: Backward pass (analytical autodiff gradients)
    grad = 2.0 * (y_pred - y) / len(X)
    dw = X.T @ grad
    db = np.sum(grad, axis=0)
    # Step 5: Optimiser parameter update step
    w -= lr * dw
    b -= lr * db

print(f"Trained parameter w: {w[0, 0]:.4f} (target: 2.0000)")
print(f"Trained parameter b: {b[0]:.4f} (target: 1.0000)")
print(f"Final training loss: {loss:.4f}")

Common pitfalls

  • Omitting `optimiser.zero_grad()`, causing gradients to compound across batches and producing exploding parameter values in the first epoch.
  • Evaluating validation data inside `model.train()`, which contaminates predictions with stochastic dropout noise and calculates batch statistics on test splits.
  • Accumulating the autograd graph by writing `total_loss += loss` instead of `total_loss += loss.item()`, exhausting host or accelerator memory.

06 Check yourself

Q1What occurs if a developer forgets to call optimiser.zero_grad() between mini-batch iterations?

Why: PyTorch accumulates gradients into parameter `.grad` buffers by default. Without zeroing, gradients from all prior batches sum together, rapidly destabilising training.

Q2Why is wrapping the validation loop in with torch.no_grad(): strongly recommended?

Why: During validation, gradients are never computed. Disabling graph tracking prevents PyTorch from allocating memory for intermediate forward activations, avoiding out-of-memory errors.

Q3Why should running loss be accumulated using loss.item() rather than the loss tensor itself?

Why: A PyTorch loss tensor contains pointers to the backward computational graph. Retaining it prevents garbage collection of the graph, quickly exhausting available system or GPU RAM.

Q4What is the primary operational benefit of gradient accumulation across multiple micro-batches?

Why: By executing multiple forward and backward passes before calling `optimiser.step()`, gradient accumulation aggregates gradients over multiple smaller micro-batches, simulating a much larger batch size on hardware with restricted VRAM.
