Evaluating LLMs: benchmarks and judges

Evaluating Large Language Models requires rigorous, multi-faceted methodologies to assess reasoning, domain knowledge, coding competence, and conversational alignment. The evaluation ecosystem balances automated standardised benchmarks (MMLU for multidisciplinary knowledge, GSM8K for multi-step arithmetic, HumanEval for code synthesis via pass@k) with model-based LLM-as-a-judge frameworks and crowdsourced pairwise Elo arenas (LMSYS Chatbot Arena). Addressing benchmark contamination, position bias, and verbosity bias is essential for trustworthy assessment.

01 The idea

How do you measure the intelligence of an artificial intelligence? When models were simple classifiers, accuracy or F1 was sufficient. Today, Large Language Models write code, compose poetry, diagnose medical symptoms, and negotiate contracts. Evaluating these open-ended capabilities demands navigating a complex landscape of standardised examination benchmarks, functional execution sandboxes, and automated LLM judge panels while guarding against benchmark memorisation and evaluator bias.

The Standardised Benchmark Suite: Different benchmarks probe distinct cognitive dimensions: - MMLU (Massive Multitask Language Understanding): 57 subjects across humanities, social sciences, and STEM tested via 5-shot multiple-choice questions. - GSM8K: 8,500 grade-school math word problems testing multi-step arithmetic reasoning with strict numerical answer matching. - HumanEval: 164 hand-crafted Python programming problems evaluated by executing generated code against unit tests in a secure sandbox. - Chatbot Arena: Crowdsourced human blind pairwise comparisons evaluated via the Elo rating system to reflect real-world conversational preference.

Benchmark contamination and test set leakage: When pre-training datasets span trillions of tokens scraped from the open web, evaluation test sets are frequently ingested into training corpora. If a model has already memorised the exact solutions to benchmark questions, high test scores reflect rote memorisation rather than generalisation. Rigorous evaluation requires 8-gram or 13-gram decontamination checks and regularly rotating private evaluation splits.

The pass@k metric for generative code evaluation: Evaluating generated code via simple sampling accuracy is biased: generating 100 samples and checking if any passed gives an inflated, high-variance estimate. The pass@k metric computes the unbiased probability that at least one of k generated samples passes all unit tests, calculated combinatorially from n total samples (where n >= k).

In everyday terms

Think of evaluating candidate physicians graduating from medical school. MMLU is the written medical board exam: hundreds of multiple-choice questions assessing textbook clinical knowledge. GSM8K is the pharmaceutical dosing exam: exact arithmetic calculations where a minor decimal error is disastrous. HumanEval is the surgical simulator: you do not evaluate the beauty of the surgeon's handwriting; you run the code in a sandbox to see if the patient survives. Chatbot Arena is bedside manner evaluated by real patients in clinical trials. A trustworthy assessment requires passing all four criteria, not just acing the multiple-choice exam.

03 The maths

  1. Unbiased pass@k estimator for functional code evaluation

    \operatorname{pass}@k = \mathbb{E}_{\text{problems}} \left[ 1 - \frac{\binom{n - c}{k}}{\binom{n}{k}} \right]

    Here $n$ is total samples generated per problem ($n \ge k$), and $c$ is the number of samples that pass all unit test assertions ($c \le n$). This combinatorial formula prevents sample variance from biasing pass estimates.

  2. Elo rating system expected outcome and score update

    E_A = \frac{1}{1 + 10^{(R_B - R_A) / 400}}, \quad R_A \leftarrow R_A + K \left( S_A - E_A \right)

    Here $R_A, R_B$ are current Elo ratings for models $A$ and $B$, $E_A$ is the expected win probability for $A$, $S_A \in \{1, 0.5, 0\}$ is the actual outcome (win, tie, loss), and $K$ is the update scaling factor.

  3. G-Eval multi-criteria weighted expectation

    \operatorname{Score}(y) = \sum_{s=1}^5 s \cdot P(\text{score} = s \mid x, y, \mathcal{R})

    Instead of taking a single greedy token rating, G-Eval computes the expected score across the top score token probabilities under rubric $\mathcal{R}$, yielding continuous, lower-variance human alignment.

04 Key takeaways

  • LLM evaluation combines standardised benchmarks (MMLU, GSM8K), functional code execution (HumanEval), and human/LLM pairwise judging.
  • Benchmark contamination must be actively monitored using n-gram decontamination scans to distinguish true reasoning from training memorisation.
  • The pass@k metric computes unbiased functional code execution probabilities without sampling distortion.
  • LLM-as-a-judge provides scalable open-ended evaluation, but requires position swapping and length controls to neutralise cognitive biases.
  • Crowdsourced blind arena evaluations (like Chatbot Arena) quantify real-world conversational utility using the Elo rating system.

05 In code

python
import math
import numpy as np

def compute_pass_at_k(n, c, k):
    """
    Unbiased pass@k estimator (Chen et al., 2021).
    n: total samples generated per problem
    c: number of samples that passed all unit tests
    k: k-threshold to evaluate
    """
    if n - c < k:
        return 1.0
    return 1.0 - (math.comb(n - c, k) / math.comb(n, k))

def update_elo(rating_a, rating_b, score_a, k_factor=32):
    """
    Compute Elo rating update for Model A and Model B.
    score_a: 1.0 for A win, 0.5 for tie, 0.0 for B win.
    """
    # Expected outcome for A
    expected_a = 1.0 / (1.0 + 10.0 ** ((rating_b - rating_a) / 400.0))
    expected_b = 1.0 - expected_a
    
    score_b = 1.0 - score_a
    new_rating_a = rating_a + k_factor * (score_a - expected_a)
    new_rating_b = rating_b + k_factor * (score_b - expected_b)
    
    return round(new_rating_a, 1), round(new_rating_b, 1)

# 1. Evaluate pass@k on a mock coding problem
n_samples = 20
c_passed = 6   # 6 of 20 samples passed unit tests

print("1. Functional Code Evaluation (pass@k):")
print(f"  Total samples generated (n): {n_samples}")
print(f"  Passed unit tests (c):       {c_passed}")
for k in [1, 5, 10]:
    pass_k = compute_pass_at_k(n_samples, c_passed, k)
    print(f"  pass@{k:2d}: {pass_k * 100:.2f}%")

# 2. Simulate LMSYS Chatbot Arena Elo updates
print("\n2. LMSYS Pairwise Tournament Elo Ratings:")
model_ratings = {"Model_Alpha": 1000.0, "Model_Beta": 1000.0}

# Match 1: Alpha beats Beta
r_a, r_b = update_elo(model_ratings["Model_Alpha"], model_ratings["Model_Beta"], score_a=1.0)
model_ratings["Model_Alpha"] = r_a
model_ratings["Model_Beta"] = r_b
print(f"  After Round 1 (Alpha wins): Alpha={r_a}, Beta={r_b}")

# Match 2: Alpha beats Beta again
r_a, r_b = update_elo(model_ratings["Model_Alpha"], model_ratings["Model_Beta"], score_a=1.0)
model_ratings["Model_Alpha"] = r_a
model_ratings["Model_Beta"] = r_b
print(f"  After Round 2 (Alpha wins): Alpha={r_a}, Beta={r_b}")

# Match 3: Beta wins Round 3
r_a, r_b = update_elo(model_ratings["Model_Alpha"], model_ratings["Model_Beta"], score_a=0.0)
model_ratings["Model_Alpha"] = r_a
model_ratings["Model_Beta"] = r_b
print(f"  After Round 3 (Beta wins):  Alpha={r_a}, Beta={r_b}")

Common pitfalls

  • Evaluating code synthesis by string matching: Using BLEU or exact match to evaluate code fails because variable names and formatting differ widely; always evaluate code by executing unit tests in an isolated sandbox.
  • Over-interpreting MMLU benchmark gains: Multiple-choice benchmarks are susceptible to guessing artifacts, prompt formatting sensitivities, and test set contamination. Do not rely on MMLU alone as an indicator of general intelligence.
  • Ignoring verbosity bias in LLM evaluators: Judge models systematically prefer longer responses even when extra sentences contain repetitive fluff or subtle hallucinations. Enforce strict word count parity or explicitly penalise verbosity in rubrics.
  • Evaluating on public benchmark test sets without rotation: As soon as a benchmark becomes popular, its questions appear in training web scrapes. Maintain held-out, privately curated evaluation sets for reliable internal benchmarking.

06 Check yourself

Q1Why is the combinatorial pass@k formula used to evaluate code generation benchmarks rather than taking simple sample averages?

Why: Evaluating pass@k by generating only k samples requires thousands of trials to obtain low variance. Generating n samples (e.g. n=100) and calculating the analytical expectation of drawing at least one passing sample out of k yields an unbiased, low-variance estimate.

Q2What is test set contamination in the context of Large Language Model pre-training?

Why: Because pre-training crawls billions of web pages (including GitHub repos, exam cheat sheets, and research papers), benchmark problems frequently leak into training data. High scores then reflect training memorisation rather than authentic problem-solving.

Q3How does the LMSYS Chatbot Arena evaluate model alignment and conversational quality?

Why: Chatbot Arena presents users with two anonymous models answering the same user prompt side by side. Users vote on which response is better, and match results are aggregated using Elo rating mathematics, mirroring competitive chess rankings.
