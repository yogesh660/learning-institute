Experiment Tracking: Systematic Machine Learning Lifecycle Logging

Logging hyperparameters, training metrics, code hashes, dataset versions, and model artifacts to ensure auditability and scientific reproducibility.

01 The idea

Machine learning development is fundamentally iterative and empirical: data scientists test dozens of model architectures, feature subsets, and hyperparameter combinations. Without systematic experiment tracking, critical institutional knowledge is lost in terminal outputs, scripts become irreproducible, and identifying which exact run produced the production model becomes impossible.

An ad-hoc approach to ML relies on manual naming conventions (`model_v2_final_really.pkl`), local notes, and memory. This quickly breaks down when teams scale or when models must be audited months later.

Modern experiment tracking platforms (such as MLflow, Weights & Biases, Comet, and Neptune) formalise every training iteration as an immutable "run" that logs three core categories of information: inputs, outputs, and metadata.

Inputs include git commit SHA, uncommitted code diffs, data version hashes (e.g. DVC commit), and hyperparameter dictionaries. Outputs include epoch-by-epoch loss curves, evaluation metrics (AUC, F1, RMSE), confusion matrices, and serialized model artifacts.

Metadata tracks hardware environment (GPU type, CUDA version), Python package dependency locks (`requirements.txt`), execution timestamp, and execution author. This structured logging enables multi-run comparisons, leaderboard ranking, and automated lineage auditing.

In everyday terms

Imagine a pharmaceutical laboratory testing hundreds of chemical compounds for a new vaccine. If scientists write recipes on loose napkins and throw away temperature logs once an experiment fails, they will inadvertently repeat dead ends and cannot prove to regulatory inspectors which exact process yielded the successful cure. Experiment tracking is the immutable, timestamped laboratory notebook of machine learning.

02 Step by step

  1. Instrumentation: Initialize an experiment client and wrap training scripts with automated logging callbacks or context managers (`mlflow.start_run()`).
  2. Parameter logging: Record complete configuration payloads (learning rate, tree depth, batch size, feature lists) at run initialization.
  3. Metric streaming: Log training and validation loss curves at every epoch or step to detect overfitting and training divergence.
  4. Artifact registration: Log serialized model checkpoints, diagnostic plots (ROC curves, calibration curves), and dependency manifests.
  5. Lineage tagging: Tag the run with git commit hash, dataset commit ID, and author to ensure total end-to-end provenance.

03 The maths

  1. Deterministic Run Provenance Tuple

    \mathcal{R} = \left( \mathcal{C}_{\mathrm{git}}, \mathcal{D}_{\mathrm{hash}}, \Theta_{\mathrm{params}}, \mathcal{E}_{\mathrm{env}}, \mathcal{M}_{\mathrm{metrics}}, \mathcal{A}_{\mathrm{artifact}} \right)

    A fully specified experiment run $\mathcal{R}$ binds the code commit, data hash, hyperparameter configuration, environment lock, evaluated metrics, and saved binary artifacts.

  2. Metric Trajectory Series

    \mathcal{T}_m = \left\{ (s, t, v_s) \;\middle|\; s \in \{1, \dots, S\}, \; v_s = m(f_{\theta_s}(X_{\mathrm{val}}), y_{\mathrm{val}}) \right\}

    Experiment tracking logs timestamped metric evaluations across training steps $s$ to reconstruct full learning trajectories.

  3. Model Checkpoint Lineage Verification

    \mathrm{SHA256}(\mathcal{A}) = \mathrm{RegistryMatch}(\mathcal{R}_{\mathrm{id}})

    Cryptographic hashing verifies that a production-deployed binary artifact exactly matches the recorded experiment run.

04 Key takeaways

  • Experiment tracking captures parameters, metrics, code revisions, and artifacts for every model run.
  • Prevents loss of empirical findings and eliminates ad-hoc filename versioning.
  • Provides auditable lineage connecting production model binaries back to their exact training data and code.
  • Enables multi-run metric comparisons, loss curve visualisations, and leaderboard ranking.

05 In code

python
import json
import hashlib
import time

class MiniExperimentTracker:
    def __init__(self, experiment_name: str):
        self.experiment_name = experiment_name
        self.runs = []

    def log_run(self, params: dict, metrics: dict, code_commit: str, data_hash: str):
        run_record = {
            'run_id': hashlib.sha1(f"{time.time()}_{params}".encode()).hexdigest()[:8],
            'timestamp': time.strftime("%Y-%m-%dT%H:%M:%SZ", time.gmtime()),
            'code_commit': code_commit,
            'data_hash': data_hash,
            'params': params,
            'metrics': metrics
        }
        self.runs.append(run_record)
        return run_record

# Simulate tracking two model experiments
tracker = MiniExperimentTracker(experiment_name="churn-prediction")

# Run 1: Baseline Random Forest
run_1 = tracker.log_run(
    params={'model': 'RandomForest', 'n_estimators': 100, 'max_depth': 6},
    metrics={'val_auc': 0.812, 'val_logloss': 0.425},
    code_commit='git_a4f10c',
    data_hash='dvc_98b1e2'
)

# Run 2: Tuned Gradient Boosting
run_2 = tracker.log_run(
    params={'model': 'LightGBM', 'learning_rate': 0.05, 'max_depth': 5},
    metrics={'val_auc': 0.849, 'val_logloss': 0.381},
    code_commit='git_c7b20e',
    data_hash='dvc_98b1e2'
)

# Compare runs
print(f"Logged {len(tracker.runs)} runs in '{tracker.experiment_name}':")
for r in tracker.runs:
    print(f"Run {r['run_id']} | Model: {r['params']['model']} | AUC: {r['metrics']['val_auc']}")

Common pitfalls

  • Logging only summary metrics: Forgetting to log the git commit hash or dataset snapshot makes a run impossible to reproduce even if metrics look outstanding.
  • Metric logging bottleneck: Sending high-frequency metrics across a remote network on every single micro-batch degrades GPU training throughput.
  • Uncommitted code changes: Running experiments with dirty git working directories logs a commit hash that does not actually reflect the code that ran.

06 Check yourself

Q1Which set of elements is essential to guarantee complete reproducibility of a machine learning experiment run?

Why: Reproducibility requires knowing the exact code commit, immutable training dataset version, configuration parameters, dependencies, and initial random seeds.

Q2What is a common performance pitfall when logging training metrics during deep neural network training?

Why: Synchronous HTTP API calls inside tight GPU training loops cause GPUs to sit idle waiting for network round-trips. Metrics should be buffered or logged asynchronously.

Q3Why should dataset version hashes (e.g. via DVC or LakeFS) be logged alongside hyperparameter configurations?

Why: If the underlying data changes, re-running identical code with identical hyperparameters produces an entirely different model unless the exact dataset version was logged.
