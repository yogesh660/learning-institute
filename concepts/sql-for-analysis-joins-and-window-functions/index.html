01 The idea

Data extraction for machine learning and analytics rarely begins with clean flat files. Relational data stores demand sophisticated joins to link entity tables and window functions to compute running totals, temporal lags, and rank orders without collapsing row granularity. Mastering set-based query execution prevents insidious silent data duplication and preserves temporal integrity.

Imagine working at a retail bank where customer records live in one table and daily account transactions live in another. To calculate each customer's lifetime transaction balance, a standard GROUP BY customer_id works fine, collapsing hundreds of individual receipts into a single summary row per customer. But what if you need to know how each individual transaction compares to that customer's rolling 30-day average, or how long elapsed since their previous deposit? A standard GROUP BY destroys the individual transaction rows, making it impossible to evaluate transaction-level anomalies.

Window functions solve this dilemma by performing calculations across a set of related table rows (the window) while keeping every original row intact in the output. Using the OVER (PARTITION BY customer_id ORDER BY transaction_date) clause, the database segments data into independent customer buckets, sorts transactions chronologically, and slides a calculation frame across them. Functions like LAG() look directly into previous rows to calculate inter-transaction arrival times, while ROW_NUMBER() or DENSE_RANK() index sequences for deduplication.

Joining tables introduces another critical hazard: cardinality explosion. An INNER JOIN preserves only matching keys, an OUTER JOIN retains unattached records by padding with NULLs, and a LEFT JOIN keeps all left-hand records. However, if the joining key has non-unique duplicates on the right (e.g. joining customer accounts to multiple shipping addresses without filtering), the join silently multiplies rows ($m \times n$ Cartesian explosion), inflating downstream aggregates like sum of revenue and silently distorting predictive model features.

In everyday terms

Running a transparent magnifying glass along an organised chronological paper ledger to compute running totals in the margin, without cutting or combining any receipts.

02 Step by step

  1. Inspect join key uniqueness: verify whether primary and foreign keys have 1-to-1, 1-to-many, or many-to-many cardinality before writing the JOIN predicate.
  2. Choose the appropriate join type: use LEFT JOIN to retain base observational cohorts with unattached entities, filtering NULLs explicitly where required.
  3. Formulate the window specification: define PARTITION BY to establish the boundary of aggregation (e.g. per user or per product category).
  4. Specify chronological ordering with ORDER BY inside the window clause to ensure deterministic sequential calculations (mandatory for LAG, LEAD, and running sums).
  5. Define the frame clause (ROWS BETWEEN ... PRECEDING AND CURRENT ROW) to prevent future leakage when computing rolling historical metrics for time-series and predictive modelling.

03 The maths

  1. Relational join cardinality and Cartesian expansion

    $$|R \bowtie_{R.k = S.k} S| = \sum_{v \in \text{dom}(k)} n_R(v) \cdot n_S(v)$$

    Here $n_R(v)$ and $n_S(v)$ are the occurrence counts of key value $v$ in tables $R$ and $S$. When key $v$ is non-unique in both tables ($n_R(v) > 1, n_S(v) > 1$), row counts expand multiplicatively, distorting downstream counts and metric sums.

  2. Window partition aggregation operator

    $$W_f(t) = f\Big(\{u \in R \mid \text{part}(u) = \text{part}(t) \;\wedge\; u \in \text{frame}(t)\}\Big)$$

    For each row $t$, $\text{part}(t)$ identifies its partition subset, $\text{frame}(t)$ defines the active evaluation window (e.g. preceding rows), and $f$ is the analytic operator (SUM, AVG, RANK). Crucially, row $t$ retains its distinct identity and granularity in the output relation.

  3. Discrete relative rank and dense rank

    $$\text{rank}(t) = 1 + \sum_{u \in \text{part}(t)} \mathbf{1}_{\text{ord}(u) < \text{ord}(t)}, \qquad \text{dense\_rank}(t) = 1 + \big|\{\text{ord}(u) \mid u \in \text{part}(t), \text{ord}(u) < \text{ord}(t)\}\big|$$

    Here $\text{ord}(t)$ represents the sorting key. Standard RANK() leaves gaps after duplicate ties (e.g. ranks 1, 2, 2, 4), whereas DENSE_RANK() advances sequentially without skipping integer positions (1, 2, 2, 3), making it preferable for pagination and top-$k$ filtering.

04 Key takeaways

  • Retention of row granularity: window functions evaluate aggregate statistics across partitions while preserving individual transaction-level rows.
  • Join cardinality awareness: many-to-many joins silently duplicate rows, artificially inflating metrics and distorting model training sets.
  • Leakage-safe framing: rolling window queries for machine learning must strictly bound frame windows to ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW to avoid future leakage.

05 In code

python
import sqlite3

conn = sqlite3.connect(":memory:")
c = conn.cursor()
c.executescript("""
CREATE TABLE users (user_id INT, tier TEXT);
INSERT INTO users VALUES (101, 'Gold'), (102, 'Silver'), (103, 'Bronze');
CREATE TABLE tx (tx_id INT, user_id INT, amount REAL, dt TEXT);
INSERT INTO tx VALUES (1, 101, 50.0, '2026-01-01'), (2, 101, 120.0, '2026-01-03'),
                      (3, 102, 200.0, '2026-01-02'), (4, 101, 30.0, '2026-01-06');
""")

query = """
SELECT u.user_id, u.tier, t.dt, COALESCE(t.amount, 0.0) AS amt,
       SUM(t.amount) OVER (PARTITION BY u.user_id ORDER BY t.dt
                           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cum_amt,
       LAG(t.amount, 1, 0.0) OVER (PARTITION BY u.user_id ORDER BY t.dt) AS prev_amt
FROM users u
LEFT JOIN tx t ON u.user_id = t.user_id
ORDER BY u.user_id, t.dt;
"""
for row in c.execute(query).fetchall():
    print(row)

Common pitfalls

  • Accidental Cartesian fan-out: joining on non-unique columns causes row explosion, quietly multiplying calculated revenues and counts.
  • Default window framing trap: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW treats identical timestamp ties as simultaneous, grouping them together instead of calculating row-by-row.
  • NULL handling in joins: NULL = NULL evaluates to UNKNOWN in SQL three-valued logic, causing equality join conditions to drop matching NULL rows unless explicit IS NOT DISTINCT FROM is specified.

06 Check yourself

Q1What is the primary difference between an analytical window function and a standard GROUP BY aggregation?

Why: Standard GROUP BY collapses all rows belonging to a group into a single summary row. A window function computes the aggregate across the partition while returning every original row with its computed window value attached.

Q2When joining two tables where the join key appears 3 times in table A and 4 times in table B, how many rows will an INNER JOIN generate for that specific key?

Why: Relational joins perform a Cartesian product over matching key values. A key with 3 occurrences in table A and 4 occurrences in table B yields $3 \times 4 = 12$ rows, potentially multiplying metric sums by 4.

Q3Why is it critical to specify ROWS BETWEEN ... PRECEDING AND CURRENT ROW rather than relying on default window framing when computing rolling features for ML?

Why: In standard SQL, specifying ORDER BY without an explicit frame defaults to RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. When multiple rows share the same order timestamp, RANGE includes all peer rows up to the end of the tie group, leaking concurrent or future information.
