01 The idea

Automated planning enables autonomous agents to synthesize sequences of actions that transition an environment from an initial state to a desired goal state. The Stanford Research Institute Problem Solver (STRIPS) formalism structures actions into preconditions, add lists, and delete lists, enabling powerful heuristics derived from planning graphs and relaxed problem spaces.

In basic pathfinding (like finding a route in a maze), states are atomic coordinates. In classical planning, the world is described by conjunctions of factual fluents (e.g. `At(Robot, RoomA) \land Has(Robot, Key)`). The challenge is that the state space is combinatorially huge: 100 binary fluents produce $2^{100}$ possible world states.

STRIPS makes planning tractable by giving actions internal structure: each action specifies what must be true before it can execute (Preconditions), what becomes true after execution (Add list), and what ceases to be true (Delete list). Planners can search forward from the initial state (progression), backward from the goal state (regression), or construct a Planning Graph (Graphplan) to extract mutual exclusions and compute admissible heuristic distances.

In everyday terms

Planning is like a flight routing dispatcher coordinating planes and crew. An action ("Fly aircraft from London to Tokyo") has strict preconditions (plane at Heathrow, crew rested, fuel filled) and effects (plane is in Tokyo, fuel is consumed, crew is duty-timed). The planner builds a flight schedule that satisfies all passenger travel goals without violating physical operational constraints.

02 Step by step

  1. Define problem specification: identify fluents describing the initial state $S_0$ and conjunction of goal literals $G$.
  2. Formulate action schemas: define actions with parameters, `Preconditions`, `Add-list` (newly asserted fluents), and `Delete-list` (negated fluents).
  3. Select search direction: choose progression search (forward from $S_0$), regression search (backward from $G$), or planning graph expansion.
  4. Compute heuristic guidance: extract delete-relaxation heuristics (e.g. $h_{\text{FF}}$ or $h_{\max}$) by ignoring all action delete lists.
  5. Enforce mutex constraints: in Graphplan, identify mutually exclusive actions and propositions across alternating action and state levels.
  6. Extract plan: backtrack through the search graph to extract a conflict-free sequence of instantiated actions achieving all goal literals.

03 The maths

  1. STRIPS State Transition Function

    \text{Result}(S, a) = (S \setminus \text{Delete}(a)) \cup \text{Add}(a), \quad \text{where} \quad \text{Precond}(a) \subseteq S

    An action $a$ is applicable in state $S$ if all preconditions are satisfied; execution removes the delete list and merges the add list.

  2. Delete-Relaxation Heuristic ($h^+$)

    h^+(S) = \min_{P \in \text{Plans}} \text{Cost}(P) \quad \text{in relaxed problem with} \quad \text{Delete}(a) = \emptyset

    Admissible heuristic obtained by dropping all negative effects (delete lists), meaning achieved fluents persist indefinitely.

04 Key takeaways

  • STRIPS actions define preconditions, add lists, and delete lists over symbolic world state fluents.
  • Delete-relaxation heuristics drop negative effects to construct fast, admissible distance estimates to goal satisfaction.
  • Planning graphs identify mutual exclusions between conflicting actions and propositions to prune impossible schedules.

05 In code

python
class STRIPSAction:
    def __init__(self, name, preconds, add_list, delete_list):
        self.name = name
        self.preconds = set(preconds)
        self.add_list = set(add_list)
        self.delete_list = set(delete_list)

    def is_applicable(self, state):
        return self.preconds.issubset(state)

    def apply(self, state):
        return (state - self.delete_list) | self.add_list

def forward_state_planner(initial_state, goal_state, actions, max_depth=10):
    """Simple breadth-first progression forward planner."""
    queue = [(initial_state, [])]
    visited = set()
    
    while queue:
        state, plan = queue.pop(0)
        state_key = frozenset(state)
        
        if goal_state.issubset(state):
            return plan
            
        if state_key in visited or len(plan) >= max_depth:
            continue
        visited.add(state_key)
        
        for action in actions:
            if action.is_applicable(state):
                next_state = action.apply(state)
                queue.append((next_state, plan + [action.name]))
    return None

# Blocks World scenario: Robot must stack Block A on Block B
actions = [
    STRIPSAction("PickUp(A)", preconds=["OnTable(A)", "Clear(A)", "HandEmpty"],
                 add_list=["Holding(A)"], delete_list=["OnTable(A)", "Clear(A)", "HandEmpty"]),
    STRIPSAction("Stack(A, B)", preconds=["Holding(A)", "Clear(B)"],
                 add_list=["On(A, B)", "HandEmpty", "Clear(A)"], delete_list=["Holding(A)", "Clear(B)"])
]

init_state = {"OnTable(A)", "Clear(A)", "Clear(B)", "HandEmpty"}
goal = {"On(A, B)"}

plan = forward_state_planner(init_state, goal, actions)
print("Automated STRIPS Planning Result:")
print(f"Goal: {goal}")
print(f"Generated Plan: {plan}")

Common pitfalls

  • Suffering from the "Sussman Anomaly" in naive goal decomposition where solving one goal inadvertently destroys an already satisfied goal.
  • Allowing state-space explosion in forward search without informative domain-independent heuristics like Fast-Forward ($h_{\text{FF}}$).

06 Check yourself

Q1What is the "delete list" of an action in the STRIPS planning formalism?

Why: In STRIPS, execution of an action deletes the fluents in its delete list from the current world state.

Q2Why is the delete-relaxation heuristic $h^+$ admissible for $A^*$ search?

Why: Dropping negative effects removes obstacles without adding new ones, guaranteeing that the relaxed optimal path is shorter than or equal to the true path cost.

Q3What is a "mutex" (mutual exclusion) relation between two actions in Graphplan?

Why: Two actions are mutex if they interfere with each other (e.g. one deletes an effect or precondition of the other) or have competing preconditions.
