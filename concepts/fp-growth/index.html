FP-growth: Frequent Pattern Mining Without Candidate Generation

Mining frequent itemsets efficiently using a compact FP-tree structure and recursive divide-and-conquer, bypassing costly candidate generation.

01 The idea

While the classical Apriori algorithm requires repeatedly scanning the entire transaction database to test millions of combinatorial candidate sets, FP-growth (Frequent Pattern Growth) compresses the transaction database into a compact prefix-tree structure called an FP-tree. Frequent itemsets are then discovered through recursive conditional pattern tree projections without generating candidate combinations.

Frequent pattern mining searches for combinations of items that appear in transactions above a user-specified minimum support threshold $s_{\min}$. In retail market basket analysis, web navigation tracking, and telemetry mining, transactions often share common subsets of items.

The bottleneck of Apriori is the candidate generation step $L_k \to C_{k+1}$, where combinatorial explosion generates vast candidate sets that require expensive multi-pass disk reads. FP-growth eliminates candidate generation by scanning the database only twice: the first scan counts 1-item supports to discard infrequent items, and the second inserts sorted frequent items into a compact Trie-like FP-tree.

In an FP-tree, transactions sharing frequent prefixes share identical tree nodes, dramatically compressing memory usage. An auxiliary header table maintains linked lists chaining all occurrences of each item throughout the tree.

FP-growth mines patterns from the bottom of the header table up (from least frequent to most frequent). For each item, it extracts its conditional pattern base (prefix paths leading to the item), builds a small conditional FP-tree, and recursively extracts frequent itemsets. Divide-and-conquer transforms a global search problem into localized branch projections.

In everyday terms

Imagine taking inventory across thousands of supermarket receipts. Apriori checks whether milk and bread frequently appear together by rescanning all paper receipts, then rescans again for triples and quadruples. FP-growth instead merges identical shopping paths into a single branching tree where shared prefixes share nodes with visit counters. Finding patterns then becomes tracing paths backwards from item leaves rather than repeatedly shuffling through paper receipts.

02 Step by step

  1. Scan database pass 1: Count support for all individual items. Filter out items with support below $s_{\min}$. Sort remaining frequent 1-items in descending order of frequency (F-list).
  2. Scan database pass 2: For each transaction, filter out infrequent items, sort remaining items according to the F-list, and insert the sorted sequence into the FP-tree, incrementing node counts and linking items via the header table.
  3. Bottom-up traversal: For each item in the header table starting from the least frequent, trace parent pointers upward to gather its conditional pattern base (sub-paths and branch path counts).
  4. Construct conditional FP-tree: Accumulate item counts within the conditional pattern base. Retain items meeting minimum support and build the smaller conditional FP-tree.
  5. Recursive divide-and-conquer: If the conditional tree contains a single path, enumerate all combinations directly. Otherwise, recursively mine the conditional tree and concatenate the base item.

03 The maths

  1. Support and Minimum Support Threshold

    \mathrm{supp}(X) = \frac{|\{T \in \mathcal{D} : X \subseteq T\}|}{|\mathcal{D}|} \ge s_{\min}

    An itemset $X$ is frequent if its relative support within the transactional database $\mathcal{D}$ meets or exceeds the minimum support threshold $s_{\min} \in (0, 1]$.

  2. Conditional Pattern Base Representation

    \mathcal{B}_i = \left\{ (p_k, c_k) \;\middle|\; p_k = \mathrm{prefix}(v_k), \; c_k = \mathrm{count}(v_k), \; v_k \in \mathrm{nodes}(i) \right\}

    The conditional pattern base for item $i$ consists of prefix paths $p_k$ leading from the root to each node $v_k$ containing item $i$, weighted by the count $c_k$ of node $v_k$.

  3. Conditional FP-Tree Node Count Projection

    \mathrm{supp}_{\mathcal{B}_i}(x) = \sum_{(p_k, c_k) \in \mathcal{B}_i : x \in p_k} c_k

    An item $x$ is retained in the conditional FP-tree for item $i$ only if its aggregated count across all prefix paths in $\mathcal{B}_i$ meets the minimum support threshold.

04 Key takeaways

  • FP-growth avoids candidate generation, scanning the transactional database only twice.
  • The FP-tree compactly encodes transactions by merging identical prefixes, saving substantial RAM.
  • Header tables with horizontal linked lists enable rapid extraction of conditional pattern bases.
  • Mining is recursive and divide-and-conquer: each conditional FP-tree operates on a fraction of the original data.

05 In code

python
import collections
from typing import Dict, List, Optional, Set, Tuple

class FPNode:
    def __init__(self, item: Optional[str], count: int, parent: Optional['FPNode']):
        self.item = item
        self.count = count
        self.parent = parent
        self.children: Dict[str, 'FPNode'] = {}
        self.node_link: Optional['FPNode'] = None

class FPTree:
    def __init__(self, min_support: int):
        self.min_support = min_support
        self.root = FPNode(None, 0, None)
        self.header_table: Dict[str, Tuple[int, Optional[FPNode]]] = {}

    def fit(self, transactions: List[List[str]]):
        counts = collections.Counter(item for txn in transactions for item in txn)
        frequent = {item: c for item, c in counts.items() if c >= self.min_support}
        if not frequent:
            return
        
        # Sort frequent items descending by frequency
        f_list = sorted(frequent.keys(), key=lambda x: (-frequent[x], x))
        order = {item: i for i, item in enumerate(f_list)}
        
        # Initialise header table: item -> [count, head_node]
        self.header_table = {item: [frequent[item], None] for item in f_list}

        # Second pass: construct FP-tree
        for txn in transactions:
            filtered = [item for item in txn if item in frequent]
            filtered.sort(key=lambda x: order[x])
            curr = self.root
            for item in filtered:
                if item in curr.children:
                    curr.children[item].count += 1
                else:
                    new_node = FPNode(item, 1, curr)
                    curr.children[item] = new_node
                    # Link to header table
                    if self.header_table[item][1] is None:
                        self.header_table[item][1] = new_node
                    else:
                        tail = self.header_table[item][1]
                        while tail.node_link is not None:
                            tail = tail.node_link
                        tail.node_link = new_node
                curr = curr.children[item]

# Example transactions
transactions = [
    ['bread', 'milk'],
    ['bread', 'diaper', 'beer', 'eggs'],
    ['milk', 'diaper', 'beer', 'cola'],
    ['bread', 'milk', 'diaper', 'beer'],
    ['bread', 'milk', 'diaper', 'cola']
]

tree = FPTree(min_support=3)
tree.fit(transactions)
print("Frequent 1-items in header:", list(tree.header_table.keys()))
# Frequent 1-items in header: ['bread', 'milk', 'diaper', 'beer']

Common pitfalls

  • If transactions have almost no shared prefixes (sparse, high-cardinality data), the FP-tree cannot compress and may consume more memory than the raw dataset.
  • Setting the minimum support threshold too low causes combinatorial explosion in the number of mined patterns, leading to out-of-memory errors.
  • Header table pointer traversals introduce pointer chasing, which can exhibit poor CPU cache locality compared to dense matrix arrays.

06 Check yourself

Q1Why is FP-growth generally significantly faster than the classical Apriori algorithm?

Why: FP-growth compresses transactions into an FP-tree in just two database scans and mines frequent patterns recursively without generating costly candidate itemsets.

Q2What purpose does the header table serve in an FP-tree?

Why: The header table maintains an item index pointing to a linked list of all occurrences of that item across tree branches, facilitating quick traversal to build conditional pattern bases.

Q3Under what condition does an FP-tree fail to provide significant memory compression?

Why: If transactions have negligible item overlap, very few prefixes can be shared, resulting in a bushy tree with almost as many nodes as total transaction items plus pointer overhead.
