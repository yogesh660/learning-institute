Train/Validation/Test Splits: Group and Time-Based

Partitioning data to mirror true production inference constraints, preventing optimistic bias caused by grouped customer records or temporal lookahead.

01 The idea

A naive random 80/20 split assumes observations are independent and identically distributed. In real-world data science, multiple rows often originate from the same patient, device, or customer, and data arrives chronologically over time. Group-aware and time-based splits enforce strict boundaries across clusters and time horizons, ensuring validation scores accurately reflect generalisation to unseen entities and future events.

Imagine building a diagnostic computer vision system to detect skin lesions. You collect 10,000 dermatoscopic images across 200 patients. If you shuffle the images uniformly into a standard 80/20 train/test split, photos from almost every patient appear in both the training set and the test set. The model can easily achieve 98% test accuracy simply by memorising patient-specific skin tones, hair patterns, lighting conditions, or hospital background tags. When you ship the model to a new clinic and test it on patient #201, performance collapses to 65% because the model learned patient identity rather than medical pathology. Group-based splitting prevents this by allocating all observations from any single patient exclusively to train or test.

A parallel disaster unfolds in temporal forecasting. Suppose you predict daily supermarket sales. If you shuffle transactions randomly across a year, the training set will contain transactions from Monday, Wednesday, and Friday, while the validation set contains Tuesday and Thursday. The model predicts Tuesday's sales using information from Wednesday and Thursday—an impossible lookahead scenario in deployment. Time-based splitting enforces the chronological arrow of time: training on historical months (e.g. January through September) and validating strictly on subsequent months (e.g. October through December).

The classic three-way partition separates concerns across the modelling lifecycle: the training set optimises internal model parameters; the validation set compares architectures, calibrates thresholds, and tunes hyperparameters; and the test set remains locked in an untouchable vault until final sign-off. Repeatedly consulting test metrics during model iteration leaks test information into human design decisions, turning the final evaluation into a disguised validation set.

In everyday terms

Testing a trainee doctor on new patients they have never examined before, rather than quizzing them on the exact same patients they observed during morning rounds.

02 Step by step

  1. Audit structural dependencies: identify whether records cluster within entities (user ID, hospital, vehicle) or follow a continuous timeline.
  2. Select splitting architecture: use GroupKFold or GroupShuffleSplit for clustered entities, and TimeSeriesSplit or chronological holdout for sequential processes.
  3. Enforce temporal embargo gaps: when features use rolling lookback windows or labels take time to resolve, insert an embargo buffer between train and test.
  4. Isolate the final test vault: seal test data prior to exploratory analysis, feature extraction, and preprocessing fitment.
  5. Verify disjoint entity boundaries: programmatically assert that the intersection between training entity identifiers and validation entity identifiers is strictly empty.

03 The maths

  1. Disjoint group partition constraint

    \mathcal{G}_{\text{train}} \cap \mathcal{G}_{\text{val}} = \emptyset, \qquad \mathcal{G}_{\text{train}} \cup \mathcal{G}_{\text{val}} \subseteq \mathcal{G}

    Where $\mathcal{G}$ represents the universe of unique entity identifiers (such as user or device IDs), and $\mathcal{G}_{\text{train}}$ and $\mathcal{G}_{\text{val}}$ are the subsets allocated to training and validation. Enforcing zero intersection ensures that no entity-specific idiosyncrasies can leak across partition boundaries.

  2. Chronological split with purge and embargo gap

    \max_{i \in \mathcal{D}_{\text{train}}} t_i < t_{\text{split}} < t_{\text{split}} + \Delta t_{\text{embargo}} \le \min_{j \in \mathcal{D}_{\text{val}}} t_j

    Where $t_i$ is the event timestamp for record $i$, $t_{\text{split}}$ is the historical cutoff, and $\Delta t_{\text{embargo}}$ is an enforced purge window. Purging eliminates records whose rolling aggregations or future outcome resolutions span across the split boundary.

  3. Expected generalisation risk under cluster shift

    \mathcal{R}_{\text{group}}(\hat{f}) = \mathbb{E}_{G \sim \mathcal{P}_G} \left[ \mathbb{E}_{(X, Y) \sim \mathcal{P}_{XY|G}} [L(Y, \hat{f}(X))] \right]

    Validation evaluates expected loss across newly drawn groups $G \sim \mathcal{P}_G$ rather than repeated draws from known training groups. This provides an unbiased estimator of true out-of-distribution performance when deploying to fresh customers or environments.

04 Key takeaways

  • Random shuffling on clustered or longitudinal data creates severe optimistic bias by rewarding models that memorise entity identities.
  • Chronological splits preserve the causal arrow of time, replicating true forward-looking production conditions.
  • Purging and embargo gaps prevent subtle leakage caused by multi-day rolling features or forward-looking label windows near split cutoffs.

05 In code

python
import numpy as np

# 1. Simulate longitudinal data: 8 entities, 5 measurements each
np.random.seed(42)
n_groups, n_obs = 8, 5
group_ids = np.repeat(np.arange(n_groups), n_obs)
# Entity random intercepts induce strong intra-group correlation
group_effects = np.random.normal(0, 5.0, size=n_groups)
X = np.random.normal(0, 1.0, size=(n_groups * n_obs, 1))
y = 2.0 * X[:, 0] + group_effects[group_ids] + np.random.normal(0, 0.5, size=n_groups * n_obs)

# Standard random split: same groups appear in both train and test
perm = np.random.permutation(len(y))
train_idx_rand, test_idx_rand = perm[:24], perm[24:]
rand_overlap = len(set(group_ids[train_idx_rand]) & set(group_ids[test_idx_rand]))

# Group-aware split: groups are partitioned disjointly
unique_groups = np.unique(group_ids)
np.random.shuffle(unique_groups)
train_groups, test_groups = unique_groups[:5], unique_groups[5:]
train_idx_grp = np.isin(group_ids, train_groups)
test_idx_grp = np.isin(group_ids, test_groups)
grp_overlap = len(set(group_ids[train_idx_grp]) & set(group_ids[test_idx_grp]))

print(f"Random split shared entity overlap: {rand_overlap} groups")
print(f"Group split shared entity overlap:  {grp_overlap} groups")
print(f"Train groups: {[int(g) for g in train_groups]}, Test groups: {[int(g) for g in test_groups]}")

Common pitfalls

  • Randomly splitting panel datasets where multiple rows originate from the same user, machine, or household.
  • Evaluating time series with standard k-fold cross-validation, allowing future information to train models predicting past events.
  • Peeking at the final test set: adjusting hyperparameters or feature selections based on test feedback invalidates unbiased generalisation guarantees.

06 Check yourself

Q1Why does standard random k-fold cross-validation yield misleadingly optimistic accuracy when applied to multi-visit hospital patient records?

Why: When multi-row records from the same patient are scattered randomly across folds, the model learns patient-specific quirks (skin tone, background artifacts) rather than generalisable disease patterns, producing false confidence.

Q2When splitting time-series data for a model forecasting demand 7 days ahead, why is an embargo or purge gap necessary at the split boundary?

Why: If features compute rolling multi-day averages or if target labels take several days to materialize, observations immediately preceding the split line may incorporate or overlap with target period data unless an embargo buffer is enforced.

Q3What is the primary role of the holdout test set compared to the validation set in a supervised learning project?

Why: Iterating on models, features, and hyperparameters against a validation set causes subtle validation overfitting. An untouched test set serves as the final arbiter of performance.
