Tokenization and Byte-Pair Encoding (BPE)

Models read numbers, not text. A tokenizer cuts text into pieces from a fixed vocabulary and gives each piece an id. Byte-Pair Encoding learns those pieces by repeatedly merging the most frequent pair.

01 The idea

A tokenizer turns "Tokenizers are unbelievably useful" into a short list of integers, one per piece. It is not a neural network and it is not trained by gradient descent: it is a fixed lookup procedure, learned once from a large text corpus, and every model is tied to the tokenizer it was trained with.

There are three obvious ways to cut text. Characters need a tiny vocabulary and never meet an unknown symbol, but sequences become very long, and attention cost grows with the square of the length. Whole words keep sequences short, but the vocabulary explodes (every name, typo and verb form) and any word not seen in training becomes an unknown [UNK]. Subwords sit in between: frequent words stay whole (the, model), rare words are split into reusable parts (for example un + believ + ably).

Byte-Pair Encoding finds those subwords automatically. Start with single characters. Count every pair of neighbouring symbols in the corpus, merge the most frequent pair into one new symbol, and repeat. Each merge adds one entry to the vocabulary; after a few tens of thousands of merges, common words are single tokens and everything else can still be spelled out from smaller pieces. To tokenize new text, the same merges are replayed in the same order.

Modern LLM tokenizers run BPE on bytes instead of characters (GPT-2, GPT-4, Llama 3). The 256 possible byte values form the base vocabulary, so any text in any language, emoji or binary junk can be encoded and nothing is ever unknown. The price is that languages under-represented in the training corpus need many more tokens for the same sentence, which makes them slower and more expensive to process.

In everyday terms

Text messaging shorthand that grows over time: people who type “thank you” often enough start writing “ty”. BPE does the same thing statistically: the most frequent pairs earn their own shortcut, rare words are still spelled out letter by letter.

02 Step by step

  1. Normalise the text if the tokenizer does that (Unicode normalisation, sometimes lower-casing; GPT-style tokenizers keep text exactly as is).
  2. Pre-tokenize: split into word-like chunks on spaces and punctuation with a regular expression, keeping the leading space as part of the word (GPT-2 shows it as Ġ, SentencePiece as ▁), so merges never cross word boundaries.
  3. Train (once): start from characters or bytes, repeatedly merge the most frequent adjacent pair, and record every merge in order until the vocabulary reaches its target size.
  4. Encode new text: split each chunk into bytes and apply the recorded merges in priority order. Look up each resulting piece in the vocabulary to get its id.
  5. Add special tokens such as <|endoftext|>, [CLS], [SEP] or chat-role markers, and pad or truncate to the context length.
  6. Decode is the reverse: ids → pieces → bytes → text. Encoding then decoding gives back the exact original string.

06 The maths

  1. One BPE merge

    $$(a^\*, b^\*) = \arg\max_{(a,b)} \operatorname{count}(a\,b), \qquad V \leftarrow V \cup \{a^\*b^\*\}$$

    Count each adjacent pair across the corpus, weighted by how often each word occurs. The winning pair becomes one symbol everywhere, and the counts are recomputed.

  2. Vocabulary size

    $$|V| = |\text{base symbols}| + \#\text{merges} + \#\text{special tokens}$$

    GPT-2: $256$ bytes $+\; 50{,}000$ merges $+\; 1$ end-of-text token $= 50{,}257$. A bigger vocabulary means shorter sequences but a larger embedding table and rarer, less well-trained tokens.

  3. WordPiece (BERT) picks merges differently

    $$\text{score}(a, b) = \frac{\operatorname{count}(ab)}{\operatorname{count}(a)\,\operatorname{count}(b)}$$

    Instead of raw frequency, it prefers pairs that occur together more often than their parts would suggest. Continuation pieces are marked with ##: un ##believ ##ably.

  4. Unigram LM (SentencePiece) works the other way round

    $$\hat{\mathbf x} = \arg\max_{\mathbf x \in S(\text{text})} \prod_i p(x_i)$$

    Start from a large candidate vocabulary and prune the pieces that hurt the corpus likelihood least. Encoding picks the most probable segmentation, and training can sample different segmentations as a form of regularisation.

  5. Why token count matters

    $$\text{attention cost} \propto T^2, \qquad T \approx \frac{\text{characters}}{4} \text{ for English}$$

    Context limits, API prices and latency are all counted in tokens. Text that tokenizes badly (rare languages, long numbers, unusual code) uses up the context window faster.

07 Key takeaways

  • A tokenizer is fixed before the model is trained; a model only understands ids from its own tokenizer.
  • BPE = start from characters or bytes, repeatedly merge the most frequent neighbouring pair, replay those merges to encode.
  • Byte-level BPE never produces an unknown token, but rare scripts and languages can take several times more tokens.
  • Many “LLM quirks” are tokenizer quirks: counting letters in a word, arithmetic on long numbers, and leading-space sensitivity.

08 In code

python
# 1) Byte-pair encoding from scratch on a toy corpus
from collections import Counter

corpus = {"low": 5, "lower": 2, "newest": 6, "widest": 3}
words = {tuple(w) + ("</w>",): c for w, c in corpus.items()}       # split into characters

def merge_step(words):
    pairs = Counter()
    for sym, c in words.items():
        for a, b in zip(sym, sym[1:]):
            pairs[a, b] += c
    (a, b), n = pairs.most_common(1)[0]
    out = {}
    for sym, c in words.items():
        new, i = [], 0
        while i < len(sym):
            if i < len(sym) - 1 and sym[i] == a and sym[i + 1] == b:
                new.append(a + b); i += 2
            else:
                new.append(sym[i]); i += 1
        out[tuple(new)] = c
    return out, (a, b, n)

for _ in range(6):
    words, m = merge_step(words)
    print("merge", m)          # ('e','s',9) ('es','t',9) ('est','</w>',9) ('l','o',7) ...

# 2) A real tokenizer (pip install tiktoken)
import tiktoken
enc = tiktoken.get_encoding("gpt2")
ids = enc.encode("Tokenizers are unbelievably useful")
print(ids, [enc.decode([i]) for i in ids], enc.n_vocab)       # 50257 tokens

# 3) Train your own byte-level BPE (pip install tokenizers)
from tokenizers import ByteLevelBPETokenizer
tok = ByteLevelBPETokenizer()
tok.train(files=["my_corpus.txt"], vocab_size=8000, min_frequency=2, special_tokens=["<|endoftext|>"])

Common pitfalls

  • Using a model with a different tokenizer than it was trained with: the ids mean different things and the output is garbage.
  • Estimating context length in words or characters; count tokens with the model’s own tokenizer.
  • Forgetting that "Hello" and " Hello" are different tokens; stray spaces in prompts change what the model sees.
  • Adding new special tokens without resizing (and training) the model’s embedding table.

09 Check yourself

Q1At each training step, BPE merges:

Why: One merge per step, chosen by frequency; the merge is then applied everywhere.

Q2Why can byte-level BPE never produce an unknown token?

Why: Any text is a sequence of bytes, and all 256 byte values are tokens.

Q3A larger vocabulary generally gives:

Why: More merges mean bigger pieces (fewer tokens per text), but each extra token needs its own row of embedding weights.

Q4To tokenize new text, a BPE tokenizer:

Why: Merge order is the priority; that makes encoding deterministic.

Q5How does WordPiece (used in BERT) decide which subword pair $(a, b)$ to merge during training, compared with standard BPE?

Why: While standard BPE greedily merges the pair with highest absolute count, WordPiece scores pairs by $\frac{\operatorname{count}(ab)}{\operatorname{count}(a)\operatorname{count}(b)}$. This penalises components that already appear frequently on their own, favouring pairs that co-occur far more often than expected by chance.

Q6In GPT-style tokenizers (such as tiktoken for GPT-2 / GPT-4), why do "apple" and " apple" (with a leading space) receive completely different token IDs?

Why: GPT tokenizers attach the leading space directly to the subsequent token (represented in GPT-2 vocab as Ġ). Because "apple" and " apple" are different byte sequences, they have separate IDs in the vocabulary table.

Q7Why do modern large language models use subword tokenization (such as BPE) rather than pure character-level or pure whole-word tokenization?

Why: Whole-word tokenizers require enormous vocabularies and choke on unseen words ([UNK]). Character tokenizers produce tiny vocabularies but inflate sequence lengths by 4–5×, which is catastrophic for $O(T^2)$ Transformer attention. Subwords strike an optimal balance between the two extremes.

Q8A custom byte-level BPE tokenizer uses the standard 256 initial byte values. During training, it executes exactly 32,000 merge operations, and the developer adds 4 special tokens (<|pad|>, <|bos|>, <|eos|>, <|unk|>). What is the final total vocabulary size $|V|$?

Why: The total vocabulary size is $|V| = |\text{base bytes}| + \#\text{merges} + \#\text{special tokens} = 256 + 32{,}000 + 4 = 32{,}260$.

Q9Unlike BPE which builds up a vocabulary bottom-up through iterative merges, how does the Unigram Language Model tokenizer (used in SentencePiece and T5) construct its final vocabulary?

Why: Unigram LM works top-down: it initialises with a large candidate pool of subwords, estimates a unigram probability for each, and iteratively discards the subwords whose removal hurts the overall training corpus likelihood the least.

Q10A toy training corpus consists of three words with word frequencies: "cost" (frequency 4), "lost" (frequency 6), and "lose" (frequency 2). Before any merges take place, which adjacent character pair has the highest count and will be selected for the first BPE merge?

Why: Counting adjacent pairs across all occurrences: ('o', 's') appears in "cost" (4), "lost" (6), and "lose" (2), giving total count $4 + 6 + 2 = 12$. Meanwhile, ('s', 't') totals $4 + 6 = 10$, and ('l', 'o') totals $6 + 2 = 8$. Therefore, ('o', 's') wins the first merge.

Q11A standard Transformer's self-attention compute cost scales quadratically with sequence length $T$ ($O(T^2)$). A short text passage tokenizes into 200 tokens in English. Due to tokenizer representation bias, the identical text in an underrepresented language tokenizes into 600 tokens ($3\times$ as many). By what factor does the attention compute cost increase for the underrepresented language?

Why: Attention cost scales with the square of sequence length: $\left(\frac{T_B}{T_A}\right)^2 = \left(\frac{600}{200}\right)^2 = 3^2 = 9.0\times$. A $3\times$ increase in token count results in a $9\times$ surge in self-attention FLOPs and memory footprint, directly impacting latency and cost.

Q12Why do modern large language models often fail at simple character-level tasks, such as counting the number of occurrences of the letter "r" in the word "strawberry"?

Why: Models never see raw character strings; they only receive integer token IDs. Because "strawberry" is parsed as subword chunks, the network has no direct access to individual letters unless explicitly prompted to spell the word out character by character.
