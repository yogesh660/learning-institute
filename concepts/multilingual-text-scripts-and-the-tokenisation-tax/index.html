Multilingual Text: Scripts, Normalisation, and the Tokenisation Tax

Scripts vary fundamentally: alphabetic (phonemic), syllabic (Japanese Kana), logographic/ideographic (Chinese Hanzi), and abjads (consonantal, right-to-left). Unicode standardisation encompasses multiple normalisation forms (NFC, NFD, NFKC, NFKD) to resolve equivalent canonical and compatibility representations. The "tokenisation tax" occurs when tokeniser vocabularies over-index on English words, fracturing non-Latin or morphologically rich text into byte fragments. Mitigation strategies include script-balanced vocabulary allocation, byte-level fallback encodings, and morphology-aware segmentation.

01 The idea

Modern NLP systems process text across diverse writing systems, from Latin and Cyrillic alphabets to logographic scripts (Chinese) and abjads (Arabic, Hebrew). Variations in Unicode normalisation forms (NFC vs NFD) and vocabulary budget allocations impose a "tokenisation tax" on non-English languages, inflating sequence lengths, inference latencies, and API serving costs.

Subword tokenisers like Byte-Pair Encoding (BPE) or WordPiece construct fixed vocabularies (e.g. 32,000 to 128,000 tokens) based on training text frequencies. Because the internet is predominantly English, vocabulary budgets are dominated by common English words and morphemes. In contrast, languages written in non-Latin scripts (such as Hindi, Arabic, Bengali, or Burmese) or morphologically agglutinative languages (like Turkish, Finnish, or Swahili) receive very few dedicated vocabulary entries. Consequently, a single sentence expressing identical semantic meaning might take 8 tokens in English, but require 35 to 45 tokens in Hindi or Amharic because characters are fragmented into individual bytes or punctuation tokens. This discrepancy—known as the tokenisation tax—means non-English speakers suffer higher monetary costs per query, shorter effective context windows, and slower generation speeds.

In everyday terms

Imagine an international telegraph service where English words have single-character Morse shorthand codes, but messages in Spanish, Japanese, or Arabic must be spelt out character by character in binary Morse pulses. Senders of non-English messages pay quadrupled line fees and wait four times as long for transmissions to finish, purely because the telegraph codebook was compiled in London.

02 Step by step

  1. Normalise incoming Unicode streams into a consistent canonical form (such as NFC) before tokenisation to avoid diacritic duplication.
  2. Examine script characteristics: handle right-to-left bidirectional flow for Arabic and Hebrew, and apply morphological segmenters for non-spaced logographic scripts (e.g. Jieba for Chinese).
  3. Analyse token fragmentation: measure average bytes per token across target language corpora to calculate the empirical tokenisation tax.
  4. Balance vocabulary allocation: use temperature-sampled multinomial data mixing during tokeniser vocabulary generation to allocate dedicated tokens to low-resource languages.
  5. Implement byte-fallback tokenisation (e.g. BBPE) to handle out-of-vocabulary characters gracefully without injecting uninformative `` unknown tokens.

04 Key takeaways

  • Unicode standardisation through NFC normalisation is essential before tokenising multilingual text.
  • The tokenisation tax leads to longer sequence lengths, reduced context windows, and inflated operational costs for non-English users.
  • Byte-level subword tokenisers with balanced vocabulary sampling help equalise cross-lingual representation efficiency.

05 In code

python
import unicodedata

def compute_tokenisation_tax(sample_texts, mock_vocab):
    """Calculates token fragmentation across different language scripts."""
    results = {}
    for lang, text in sample_texts.items():
        # Canonical Normalisation (NFC)
        norm_text = unicodedata.normalise('NFC', text)
        words = norm_text.split()
        
        # Greedy longest subword tokenisation simulation
        tokens = []
        for word in words:
            i = 0
            while i < len(word):
                matched = False
                for j in range(len(word), i, -1):
                    sub = word[i:j]
                    if sub in mock_vocab:
                        tokens.append(sub)
                        i = j
                        matched = True
                        break
                if not matched:
                    # Fallback to UTF-8 byte tokens
                    byte_tokens = [f"<byte_{b}>" for b in word[i].encode('utf-8')]
                    tokens.extend(byte_tokens)
                    i += 1
                    
        tax_ratio = len(tokens) / max(1, len(words))
        results[lang] = {
            'char_count': len(norm_text),
            'word_count': len(words),
            'token_count': len(tokens),
            'tokens_per_word': tax_ratio,
            'tokens': tokens[:6]  # First few tokens
        }
    return results

# English-centric vocabulary (typical of earlier web-crawled models)
mock_vocab = {
    "Artificial", "intelligence", "transforms", "modern", "technology",
    "La", "intelligence", "artificielle", "moderne"
}

sample_corpora = {
    "English": "Artificial intelligence transforms modern technology",
    "French": "La intelligence artificielle transforme la technologie moderne",
    "Hindi (Devanagari)": "कृत्रिम बुद्धिमत्ता आधुनिक तकनीक को बदल रही है"
}

analysis = compute_tokenisation_tax(sample_corpora, mock_vocab)

print("Multilingual Tokenisation Tax Comparison:")
for lang, stats in analysis.items():
    print(f"\n[{lang}]")
    print(f"  Words: {stats['word_count']} | Generated Tokens: {stats['token_count']}")
    print(f"  Tokens per Word: {stats['tokens_per_word']:.2f}")
    print(f"  Sample Tokens: {stats['tokens']}")

Common pitfalls

  • Neglecting Unicode normalisation (NFC vs NFD); identical looking characters like "é" (U+00E9) and "e + ́" (U+0065 U+0301) produce entirely different subword token sequences.
  • Assuming word-level whitespace splitting works for languages without spaces between words (such as Chinese, Japanese, or Thai).
  • Evaluating multilingual model latency solely on word or character counts, masking massive token count inflation for non-Latin scripts.

06 Check yourself

Q1What is the primary cause of the "tokenisation tax" in multilingual language models?

Why: Because pretraining data is predominantly English, subword merge operations allocate vocabulary entries to English words, while non-Latin scripts are fragmented into small byte sequences.

Q2Which Unicode normalisation form composes characters with their diacritical marks into precomposed code points wherever possible?

Why: NFC decomposes characters canonically and then recomposes them into standard precomposed glyphs, ensuring consistent single-character representations.

Q3In a transformer architecture with standard quadratic attention, how does a 3x tokenisation tax impact attention computation FLOPs?

Why: Standard self-attention computes an $N \times N$ affinity matrix. Tripling the sequence length ($3N$) increases attention dot-products and memory by a factor of $3^2 = 9\times$.
