Text normalisation, Unicode and regex

Raw unstructured text is fraught with encoding inconsistencies, non-standard whitespace, varying case representations, and visual homoglyphs. Text normalisation transforms raw character sequences into consistent canonical representations prior to tokenisation and language modelling. By mastering Unicode standardisation forms (NFC, NFD, NFKC, NFKD) to resolve visually identical glyph representations, deploying case folding to consolidate vocabularies, and using declarative regular expressions (regex) to strip noise and extract structured patterns (dates, URLs, phone numbers, monetary figures), natural language pipelines eliminate spurious out-of-vocabulary tokens and stabilise downstream model convergence.

01 The idea

To human eyes, the word "café" written with a precomposed acute accent character (U+00E9) looks indistinguishable from "cafe" followed by a combining acute accent (U+0065 U+0301). Yet to a computer or neural embedding layer, these represent completely different byte sequences and hash to distinct dictionary entries. A web scraper collecting user comments will encounter curly quotes, non-breaking spaces, emoticons, multiple exclamation marks, and mixed encodings. Before an algorithm can parse syntax or learn semantic embeddings, it must normalise text into clean, canonical strings.

The Unicode standard and canonical equivalence: The Unicode consortium assigns a unique code point (e.g. U+0041 for 'A') to every character across human writing systems. However, historical design compromises created multiple representations for identical glyphs: a character with an accent can be stored as a single "precomposed" code point (e.g. 'é' as U+00E9) or as a base character followed by a "combining" accent mark ('e' + '´' as U+0065 U+0301). Canonical equivalence establishes that these represent the exact same abstract character. Without Unicode normalisation, string equality tests ('é' == 'e\u0301') fail, splitting model vocabularies in two.

The four Unicode normalisation forms: Unicode standardises four normalisation algorithms: normalisation Form D (NFD, canonical decomposition, separating accents into combining marks); normalisation Form C (NFC, canonical decomposition followed by canonical composition, standardising on precomposed characters); normalisation Form KD (NFKD, compatibility decomposition); and normalisation Form KC (NFKC, compatibility decomposition followed by composition). While NFC is the web and Linux standard, compatibility forms (NFKC/NFKD) resolve typographical formatting variants—folding superscript numbers ($2^5 \to 25$), ligature glyphs ('ﬁ' $\to$ 'fi'), and full-width Asian characters into standard ASCII equivalents.

Case folding and vocabulary compression: In natural language processing, distinguishing "Apple" (the technology company) from "apple" (the fruit) requires case sensitivity; however, for many information retrieval and sentiment analysis tasks, treating "The", "the", and "THE" as three separate vocabulary tokens increases parameter memory and fragments statistical counts. Lowercasing reduces vocabulary size. In international text, standard lowercasing is insufficient: German 'ß' lowercases to 'ß', but case folding transforms it to 'ss' (allowing 'GROSS' to match 'groß'). Unicode case folding provides language-agnostic character parity.

Pattern extraction and noise filtering via Regular Expressions: Once text is canonically encoded, regular expressions (regex) provide a declarative finite-state engine for syntactic pattern matching and text sanitisation. Regex enables removing HTML tags (<[^>]+>), collapsing runs of whitespace (\s+ to single space), stripping control characters, and extracting structured semantic tokens (such as URLs, email addresses, and monetary currencies) before feeding clean text into subword tokenisers like BPE or WordPiece.

In everyday terms

Imagine a postal sorting depot receiving millions of handwritten envelopes every morning. Some senders write "NEW YORK", others write "new york", and some write "New York". Some use fountain pens with sharp accents; others tape printed address labels with typographic ligatures; others leave messy coffee cup stains (HTML tags and control codes). If the sorting machine treats every minor typographic quirk as a completely new city destination, it would need twenty thousand distinct mail sorting bins for New York alone. Text normalisation is like the initial automated intake scanner: it flattens case to canonical lowercase, strips stray postal tape marks, normalises accented characters into standard regional spellings, and cleans excess spaces. All twenty variations drop into a single, clean "new york" sorting bin with zero postal confusion.

03 The maths

  1. Unicode canonical equivalence condition

    S_1 \equiv_{\text{canonical}} S_2 \iff \operatorname{NFD}(S_1) = \operatorname{NFD}(S_2)

    Two character sequences $S_1$ and $S_2$ are canonically equivalent if and only if their normalisation Form D (NFD) decompositions yield identical sequences of Unicode code points.

  2. Unicode compatibility equivalence condition

    S_1 \equiv_{\text{compatibility}} S_2 \iff \operatorname{NFKD}(S_1) = \operatorname{NFKD}(S_2)

    Compatibility equivalence is a weaker relation that equates characters representing the same abstract meaning but possessing distinct visual typography (such as ligature 'ﬁ' $\equiv$ 'f' + 'i', or circled digit '①' $\equiv$ '1'). normalisation Form KC (NFKC) composes compatibility decompositions into canonical precomposed characters.

  3. Vocabulary reduction ratio

    \rho_{\text{vocab}} = 1 - \frac{|V_{\text{norm}}|}{|V_{\text{raw}}|}, \quad \text{OOV Rate} = \frac{N_{\text{unseen}}}{N_{\text{total\_tokens}}}

    Normalising casing and Unicode representations dramatically compresses vocabulary size $|V|$, reducing embedding table parameter memory while lowering the Out-Of-Vocabulary (OOV) rate on unseen test text.

04 Key takeaways

  • Text normalisation converts noisy, unstructured text into clean canonical strings prior to tokenisation.
  • Unicode characters can have multiple encodings; NFC and NFKC standardise precomposed and compatibility glyphs.
  • Case folding (str.casefold()) provides linguistically accurate casing parity across multilingual scripts beyond simple ASCII lowercasing.
  • Regular expressions enable declarative pattern extraction (URLs, emails, dates) and whitespace sanitisation.
  • Normalisation compresses vocabulary size and slashes Out-Of-Vocabulary (OOV) rates in downstream language models.

05 In code

python
import unicodedata
import re

# 1. Unicode Normalisation demonstration: Resolving visual homoglyphs
# Precomposed 'e' with acute accent (U+00E9) vs decomposed 'e' + combining acute (U+0065, U+0301)
str1 = "café"                  # Precomposed: '\u0063\u0061\u0066\u00e9'
str2 = "cafe\u0301"             # Decomposed:  '\u0063\u0061\u0066\u0065\u0301'

print("Raw Unicode comparison:")
print(f"str1 ('{str1}') length: {len(str1)}, bytes: {[ord(c) for c in str1]}")
print(f"str2 ('{str2}') length: {len(str2)}, bytes: {[ord(c) for c in str2]}")
print(f"Direct string equality (str1 == str2): {str1 == str2} (FAILS without normalisation)")

# Normalise using NFC (Canonical Composition)
norm1 = unicodedata.normalise('NFC', str1)
norm2 = unicodedata.normalise('NFC', str2)
print(f"After NFC normalisation (norm1 == norm2): {norm1 == norm2} (MATCHES!)\n")

# 2. Resolving Typographic Ligatures with NFKC
# Typographic ligature 'fi' (U+FB01) vs separate letters 'f' and 'i'
ligature_str = "The scientific ﬁnding"
nfkc_str = unicodedata.normalise('NFKC', ligature_str)
print(f"Raw ligature string:   '{ligature_str}' (length {len(ligature_str)})")
print(f"After NFKC normalisation: '{nfkc_str}' (length {len(nfkc_str)}, 'ﬁ' split to 'f'+'i')\n")

# 3. Unicode Case Folding
german_text = "Der Fluss ist GROSS"
casefolded = german_text.casefold()
print(f"Raw German text:       '{german_text}'")
print(f"After casefold():      '{casefolded}' ('GROSS' correctly matches 'gross')\n")

# 4. Regex Pattern Masking and Noise Sanitisation
raw_corpus = "Contact support@example.com or visit https://ai.example.org/help!  Price:   £150.00   (tax-free)."

# Extract structured entities before cleaning
url_pattern = r'https?://\S+'
email_pattern = r'[\w\.-]+@[\w\.-]+\.\w+'

urls_found = re.findall(url_pattern, raw_corpus)
emails_found = re.findall(email_pattern, raw_corpus)

# Replace structured entities with semantic tokens
clean_text = re.sub(url_pattern, '<URL>', raw_corpus)
clean_text = re.sub(email_pattern, '<EMAIL>', clean_text)

# Collapse redundant whitespace
clean_text = re.sub(r'\s+', ' ', clean_text).strip()

print("Regex Pipeline Results:")
print(f"Extracted URLs:   {urls_found}")
print(f"Extracted Emails: {emails_found}")
print(f"Sanitised Text:   '{clean_text}'")

Common pitfalls

  • Stripping accents when language meaning depends on them: In languages like Spanish or French, stripping accents alters lexical meaning ('año' = year vs 'ano' = anus; 'pêche' = peach/fishing vs 'péché' = sin); only strip accents when building broad search indexes.
  • Using naive str.lower() instead of str.casefold(): Standard lowercasing fails on multilingual characters like German 'ß' or Turkish 'I/ı', creating subtle search and tokenisation bugs.
  • Running regex punctuation stripping before URL/email extraction: Naively removing punctuation like dots and slashes destroys URLs and email addresses before they can be parsed or tokenised.
  • Over-normalising numbers and dates: Replacing all numbers with a generic token in financial or legal models destroys crucial numerical values; use tailored tokenisation where numerical magnitude matters.
  • Inconsistent normalisation between training and inference: If training data is normalised using NFKC lowercasing but live inference receives un-normalised raw Unicode, tokenisers produce disjoint embeddings and broken predictions.

06 Check yourself

Q1Why does direct string equality ('café' == 'cafe\u0301') evaluate to False in Python without Unicode normalisation?

Why: Unicode allows canonical equivalence: precomposed 'é' (U+00E9) and decomposed 'e' + combining accent (U+0065 U+0301) represent identical glyphs, but represent different byte code point sequences. Normalising with NFC or NFD standardises the representation.

Q2What is the difference between Unicode normalisation Form C (NFC) and normalisation Form KC (NFKC)?

Why: Canonical equivalence (NFC) preserves visual glyph integrity (accents). Compatibility equivalence (NFKC) goes further, folding stylistic variants—such as ligatures ('ﬁ' $\to$ 'fi'), circled numbers, and fractions—into standard alphanumeric characters.

Q3Why is str.casefold() preferred over str.lower() when preparing multilingual text for natural language processing?

Why: Lowercasing German 'ß' leaves it unchanged as 'ß', which fails to match lowercase 'ss' in 'GROSS'. Case folding maps both to 'ss', establishing true linguistic equality across diverse languages.

Q4Why should structured entities (such as URLs and email addresses) be identified and masked with regex before general punctuation removal?

Why: URLs and email addresses depend heavily on punctuation (://, ., @). If a pipeline strips punctuation first, 'https://example.com/login' is mutilated into 'https example com login', losing its semantic identity.
