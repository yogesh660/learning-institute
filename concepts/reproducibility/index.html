Reproducibility in Machine Learning: Determinism, Seeds, and Environments

Achieving scientific and production reproducibility across pseudorandom number generators, multi-threading, GPU nondeterminism, and environment locks.

01 The idea

In software engineering, compiling the same source code with the same compiler always yields identical binaries. In machine learning, however, re-running identical code on identical data often produces different weights, fluctuating metrics, and divergent decisions. Achieving true end-to-end reproducibility requires controlling random seeds, hardware thread scheduling, GPU CUDA operations, and software dependency locks.

Machine learning pipelines contain dozens of stochastic elements: train/test split sampling, random weight initialisation, minibatch shuffling, dropout masks, and tree feature subsampling. Each relies on pseudorandom number generators (PRNGs).

Setting a single seed (e.g. `np.random.seed(42)`) is insufficient because modern frameworks run multiple independent PRNGs across Python built-in `random`, NumPy, PyTorch CPU, and PyTorch CUDA.

Beyond seeds, parallel hardware execution introduces non-determinism. Multi-threaded operations like OpenMP matrix multiplications and asynchronous CUDA atomic additions sum floating point numbers in varying orders. Because floating point addition is non-associative ($ (a + b) + c \ne a + (b + c) $ due to rounding), different thread arrival orders produce different rounding errors that compound over millions of gradient steps.

Finally, environment drift (a minor patch update to scikit-learn, CUDA drivers, or BLAS linear algebra libraries) can alter default parameters or algorithmic implementations. Hermetic reproducibility requires containerised environment locks (Docker, conda-lock, or poetry.lock).

In everyday terms

Imagine following a baking recipe where the recipe specifies "add yeast and stir until bubbly". Depending on room temperature, humidity, and the vigour of your whisking, the dough rises differently every time. Achieving commercial culinary reproducibility requires an automated climate-controlled chamber, exact gram weights, and a mechanical mixer running at a fixed RPM for exactly 180 seconds.

02 Step by step

  1. Multi-engine PRNG seeding: Seed all active random generators: Python `random`, NumPy, PyTorch CPU, PyTorch CUDA, and environment variable `PYTHONHASHSEED`.
  2. Enforce algorithmic determinism: Configure deep learning frameworks to enforce deterministic algorithms (`torch.use_deterministic_algorithms(True)` and `CUBLAS_WORKSPACE_CONFIG=:4096:8`).
  3. Pin hardware concurrency: Constrain multi-threaded math libraries (MKL, OpenMP, BLAS) to fixed thread counts (`torch.set_num_threads(1)` during strict testing).
  4. Dependency locking: Export explicit hash-pinned dependency manifests (`pip freeze` with hashes, `poetry.lock`, or Docker image digest).
  5. Data version pinning: Reference immutable dataset commits using tools like DVC, LakeFS, or Delta Lake time-travel rather than mutable database tables.

03 The maths

  1. Floating Point Non-Associativity

    (a \oplus b) \oplus c \ne a \oplus (b \oplus c)

    Due to finite precision truncation in IEEE 754 floating point arithmetic, differing summation orders in parallel threads produce non-identical results.

  2. Atomic Float Accumulation Divergence

    \hat{g} = \bigoplus_{k=1}^K g_{\pi(k)}, \quad \pi \in \mathcal{S}_K

    When $K$ CUDA threads execute atomic additions, the thread arrival permutation $\pi$ varies across runs, causing slight divergence in computed gradients $\hat{g}$.

  3. Deterministic State Transition Function

    \mathcal{S}_{t+1} = f(\mathcal{S}_t, \mathcal{D}_t; \xi_t), \quad \xi_t = \mathrm{PRNG}(\sigma, t)

    Model state $\mathcal{S}$ evolves deterministically if and only if initial seed $\sigma$, dataset batch order $\mathcal{D}_t$, and framework operations $f$ are strictly invariant.

04 Key takeaways

  • True reproducibility requires seeding Python, NumPy, PyTorch, and locking `PYTHONHASHSEED`.
  • Floating point operations are non-associative; thread race conditions in multi-GPU and multi-CPU environments introduce variation.
  • Enforcing strict GPU determinism may incur a modest throughput penalty (10–20%) because fast non-deterministic atomic operations are disabled.
  • Containerisation (Docker) and pinned lockfiles guarantee identical compiler, driver, and library versions.

05 In code

python
import random
import os
import numpy as np
import torch

def set_strict_determinism(seed: int = 42):
    """Enforce complete determinism across all random number generators and hardware."""
    # 1. Python built-in and hash seed
    random.seed(seed)
    os.environ['PYTHONHASHSEED'] = str(seed)
    
    # 2. NumPy PRNG
    np.random.seed(seed)
    
    # 3. PyTorch CPU and CUDA
    torch.manual_seed(seed)
    if torch.cuda.is_available():
        torch.cuda.manual_seed(seed)
        torch.cuda.manual_seed_all(seed)
        
        # Enforce deterministic convolution algorithms
        torch.backends.cudnn.deterministic = True
        torch.backends.cudnn.benchmark = False
        
        # Configure cuBLAS workspace for deterministic operations
        os.environ['CUBLAS_WORKSPACE_CONFIG'] = ':4096:8'
    
    # Throw an error if a non-deterministic operation is invoked
    try:
        torch.use_deterministic_algorithms(True)
    except AttributeError:
        pass
    print(f"Deterministic seed locked: {seed}")

set_strict_determinism(42)

# Verify reproducible tensor operations
t1 = torch.randn(3, 3)
set_strict_determinism(42)
t2 = torch.randn(3, 3)
assert torch.equal(t1, t2), "Tensors must be strictly identical across identical seeds!"
print("Determinism verified successfully.")

Common pitfalls

  • Assuming `torch.manual_seed` seeds NumPy: PyTorch and NumPy use completely separate PRNG states; seeding one does not affect the other.
  • Multi-worker DataLoader leakage: In PyTorch DataLoaders with `num_workers > 0`, workers inherit identical seed states unless configured with a `worker_init_fn`.
  • Running on different GPU architectures: A model trained on an NVIDIA A100 vs an RTX 4090 will produce slightly different floating point weights even with identical seeds due to microarchitecture math differences.

06 Check yourself

Q1Why does multi-threaded parallel floating point summation produce different numbers across runs even with identical random seeds?

Why: Because $(a + b) + c \ne a + (b + c)$ in IEEE 754 arithmetic, changing the order in which parallel threads accumulate numbers alters the lowest-order bits.

Q2What is the consequence of setting `torch.backends.cudnn.benchmark = True` in PyTorch?

Why: `cudnn.benchmark = True` benchmarks several convolution algorithms on the fly to pick the fastest one, which may change between runs and cause non-deterministic behaviour.

Q3In a multi-worker PyTorch DataLoader (`num_workers=4`), what happens if you do not provide a custom `worker_init_fn`?

Why: Forked worker processes inherit the exact same base PRNG seed, causing each worker to perform identical augmentations on different items unless re-seeded per worker.
